ABSTRACT
Sub-4-bit quantization allows mobile devices to run larger LLMs, but its memory savings do not always translate
into faster decoding on mobile NPUs. Their matrix units support only a few native integer datatypes, and
converting unsupported weight formats on the vector unit can erase the gains from fewer bits. Mixed precision
faces an additional constraint: each matrix-unit tile uses one datatype. MixFold executes 3-bit and perfectly
symmetric 2-bit weights using native integer operations without expanding the weights to wider datatypes during
decoding. MixFold then assigns datatypes to output-channel groups aligned with the matrix-unit tiles, enabling
finer-than-layer assignment without disrupting matrix-unit execution. We compare MixFold with llama.cpp
Hexagon backend on the Qualcomm Hexagon NPU of a Snapdragon 8 Elite Gen 5. Across the Qwen3 model
family, MixFold achieves comparable or higher accuracy than llama.cpp’s sub-4-bit formats at matched bits per
weight, while decoding 1.16–1.41× faster and generating 1.5–4.3× more tokens per joule.

INTRODUCTION
Sub-4-bit quantization, below 4 bits per weight (BPW) on
average, allows a mobile device to hold a larger LLM.
Larger LLMs can better support on-device AI use cases
involving personal data such as contacts, photos, calendar
events, and messages. Two levers can improve accuracy
under a sub-4-bit budget. The first is a better datatype, such
as the perfectly symmetric 2-bit grid (Liu et al., 2025) or
3-bit weights. The second is mixed precision (MP), which
assigns more bits to sensitive weights and fewer bits to the
rest. With these additional format choices, MP can further
improve accuracy at a given BPW.
However, on mobile NPUs, the most accurate sub-4-bit con-
figurations save memory, but their decode time may not be
as fast as their bytes promise. This is because the matrix
unit of a mobile NPU admits only a few datatypes directly
in hardware. We call these datatypes native. In contrast,
non-native datatypes require converting the weights on the
vector unit before the matrix unit execution. For example,
a straightforward approach expands perfectly symmetric
2-bit and 3-bit weights to native 4-bit values on the vec-
tor unit before matrix-unit execution. A GPU could hide
such conversion with a powerful general computing capabil-

matrix unit as well. Each matrix unit tile uses one datatype,

The two levers thus set two requirements. Every datatype
in the mix must execute natively, and each weight tile must
hold one bitwidth. Existing approaches do not fulfill both
requirements at once. llama.cpp converts the weights on the
vector unit before every multiplication (The ggml authors,
2023). T-MAN skips the conversion with lookup tables

bitwidths per layer (Dong et al., 2020; Yao et al., 2026), per

et al., 2024). Per-layer assignment keeps each tile in one
bitwidth but ignores the sensitivity variation within a layer.
The finer two may assign different bitwidths within a tile.

tiled architecture. At decode, MixFold executes perfectly
symmetric 2-bit weights using native 2-bit codes by folding
the correction into the bias. For 3-bit weights, it uses bit-

Execution on Mobile NPUs. Figure 1 illustrates how a
mobile NPU executes Integer MMA, using Qualcomm’s
Hexagon NPU (Mahurin, 2023) as a representative exam-
ple. The NPU comprises four components: Hexagon Ma-
trix eXtensions (HMX), a matrix unit that performs the
MMA; Hexagon Vector eXtensions (HVX), a vector unit for
general-purpose computation; Vector Tightly Coupled Mem-
ory (VTCM), a software-managed on-chip memory shared
by HMX and HVX; and a direct memory access (DMA)
engine that moves data between main memory (DRAM) and
VTCM (Qualcomm Technologies, Inc., 2026; 2025).
HMX operates on tiles: it multiplies an activation tile by a
weight tile and accumulates the products into a T ×T output
tile. The weights, activations, and requantization parameters
reside in main memory. Since the capacity of the on-chip
memory is limited, they are staged by DMA for one output
tile at a time, which spans T activation vectors and T output
channels, and the data for the next output tile are prefetched
during the current MMA (The ggml authors, 2023). For
each output tile, the matrix unit loads successive activation
and weight tiles along the K dimension into its registers,
accumulates their products (see (2)), and then applies the
requantization with one set of parameters per output channel
(see (3) and (4)).
We call a format native when its datatype and tiled layout
match the operands consumed by the matrix unit, thereby
leading to a seamless flow of MMA and requantization;
otherwise, it is called non-native. A prime example of
a non-native format is llama.cpp’s Q4 0, which packs 32
consecutive 4-bit integer codes with a scale. This format
requires the vector unit to convert weights into a native
datatype (such as FP16) before they reach the matrix unit.

Challenges in Sub-4-Bit Quantization
Non-Native Weight Representations. Weight bitwidths
below 4 bits, namely 3 and 2 bits, reduce the memory foot-
print further. However, 3-bit weights are non-native, since
HMX provides no native MMA for 3-bit weights. Indeed,
3-bit quantization is commonly unsupported across most
NPUs, not just Hexagon, because compute units are fun-
damentally optimized for power-of-two data widths (Xia
et al., 2024; Zeng et al., 2025; Park et al., 2023). In con-
trast, 2-bit weights are native, but their grid limits accuracy.
The native 2-bit grid is the conventional signed integer grid
{−2, −1, 0, 1}, which is asymmetric about zero and cov-
ers a narrower range of positive weights than of negative
ones. Stretched Elastic Quantization (SEQ) was proposed
by ParetoQ (Liu et al., 2025) for such extreme low-bit quan-
tization and instead maintains a perfectly symmetric grid
{−3, −1, 1, 3} at 2 bits. We call this format W2-SEQ; un-
suffixed W2, W3, and W4 denote the signed integer grids.
ParetoQ reported that W2-SEQ outperforms W2 in per-
channel QAT. Figure 2 also shows that W2-SEQ yields
a higher output signal-to-quantization-noise ratio (SQNR)
than W2, and W3 comes close to W4.
Even though W3 and W2-SEQ can improve model qual-
ity under sub-4-bit quantization, their non-native repre-
sentations require runtime conversion. Since the W3 grid
{−4, . . . , 3} and the W2-SEQ grid are both contained in
the W4 grid {−8, . . . , 7}, the vector unit can expand their
weights to native W4. However, the matrix unit cannot start
the MMA until the less powerful vector unit (Hao et al.,
2026) completes this expansion. The expanded weights can-
not be retained in the limited on-chip memory, while storing
W4 copies in DRAM would forfeit the savings of fewer bits.
Consequently, the expansion must be repeated for every for-
ward pass, and its cost is amortized only over M activation
vectors: many during prefill, but one or a few during decode.
HVX also serves camera and vision workloads (Codrescu,
2015). With few HVX threads, this expansion falls behind
the weight stream at decode.

Hardware-aligned MP. MP benefits mobile NPU inference
only when latency scales with bits per weight (BPW). For
example, a 3.0-BPW model that mixes W2 and W4 should
decode approximately halfway between the uniform W2 and
W4 models. This requires that each datatype MP utilizes
achieve byte-proportional execution and that dispatching
different formats incur negligible overhead. Within these
constraints, the assignment granularity should be as fine as
possible. Layer-wise assignment (Dong et al., 2020; Yao
et al., 2026) meets both requirements but ignores sensitivity
variation within a layer. Per-channel assignment (Zheng
et al., 2026) captures this variation but may assign different
bitwidths to channels within the same weight tile, which the
matrix unit cannot process directly. Regrouping channels by
bitwidth may keep each tile in a single bitwidth, but HMX
would produce output channels in the regrouped order, re-
quiring an additional pass to restore the original channel
order. Consequently, per-channel assignment introduces
repeated conversion or reordering overhead, preventing la-
tency from scaling with BPW.

EXECUTING NON-NATIVE WEIGHTS
WITH NATIVE INTEGER MMA
As mentioned in Section 2.2, W2-SEQ and W3 lack a native
HMX MMA path. A naive approach to execute both for-
mats is to expand their weights to signed W4 when loading
them into VTCM (Section B.3); we call this the expand
path. However, the expand path makes every MMA wait
for weight conversion, and decode offers little weight reuse
to amortize this overhead. Instead, our approach keeps the
weights in native low-bit layouts and folds the remaining
work into operands whose cost scales with the activations
rather than the weights. We call these the fold paths.

3.3
Pipelined Execution and Path Selection
Pipelined execution.
For each activation-row block, the
kernel streams its weights in chunks of output-channel tiles.
DMA prefetches up to three chunks ahead into ring slots in
VTCM, and HMX multiplies a chunk once it is ready. HVX
prepares the activation layout and materializes each chunk’s
outputs. It also converts the weight chunks in the expand
path and computes the intermediate terms of the fold paths.
From HVX-bound to memory-bound.
Figure 3 shows
how the three units overlap at decode size (M = 1). In the
expand path, every chunk must pass through HVX before
HMX can use it. Converting a chunk takes about 1.9×
its DMA time for W3 and 1.4× for W2-SEQ. HMX idles
between chunks, and DMA stalls because a ring slot is freed
only after its chunk is converted and multiplied. The fold
paths remove this stage, so DMA feeds encoded low-bit
tiles directly to HMX. For W3, HMX multiplies both planes
into one accumulator (HMX-only). For W2-SEQ, HVX
computes the row sum and updates the input bias once,
before the first MAC. Both kernels are thus weight-stream-
bound, like native kernels (Table 2). The fold paths reduce
W3 and W2-SEQ latencies from 36.2 to 18.4 µs and from
20.1 to 12.2 µs, respectively. The expand path reaches the
weight-stream bound only with multiple HVX threads and
large layers, as in Qwen3-4B (Section B.3).
Cost across M and path selection.
Table 3 generalizes
this comparison to any M. The expand path converts all
NK weights on HVX in every call, regardless of M. The
fold paths never convert weights. In exchange, HMX does
more MACs than the MNK of a native kernel. The W2-
SEQ accumulator-fold and the W3 HVX-assisted activation-
fold performs MN(K+S) MACs, where one extra tile
(S = T) suffices in practice, so the overhead is T/K. Even
the 2MNK of the W3 HMX-only activation-fold is cheap,
since HMX delivers two to three orders of magnitude more
throughput than an HVX thread (Hao et al., 2026). The
trade therefore favors the fold paths at small M. As M
grows, the NK conversion is amortized over more rows,
while the activation-side work and the extra MACs keep
growing with M. The crossover therefore depends on the
MMA shape, motivating shape-dependent path selection in
MixFold (Figure 5).
4
OUTPUT-CHANNEL GROUP-WISE MP
4.1
Hardware-Aligned MP Granularity
HMX multiplies each weight tile in a single datatype (Fig-
ure 1). A weight tile spans T contiguous output channels.
Tiles along K add into the same accumulator (see (2)), so
in principle they could use different bitwidths. However, all
tiles of an output channel share one weight scale (see (4)).
Sharing a scale across tiles of different bitwidths prevents
each bitwidth from using an independently calibrated quan-
tization grid, which can introduce large quantization error.
We therefore assign bitwidths along the output channels.
The finest granularity that keeps the native tiled layout is
a group of T contiguous output channels. Each group of
a layer independently selects W2-SEQ, W3, or W4. All
tiles of a group share its bitwidth, and each output channel
keeps one scale across K. This meets both requirements of
Section 2.2.
4.2

allocation problem using an integer linear program (ILP).

EVALUATION
We evaluate MixFold with three questions. (Q1) Do the fold
paths run W3 and W2-SEQ as close to the DMA ceiling
as native kernels, and up to which M (Section 5.2)? (Q2)
Do group-wise mixed-precision kernels scale with BPW in
latency and energy (Section 5.3)? (Q3) Does group-wise
allocation improve accuracy over layer-wise allocation at the
same BPW, and do W2-SEQ and W3 add to it (Section 5.4)?
Section 5.5 then compares MixFold with llama.cpp end to
end on the same NPU.
5.1
Setup
Platform and models.
We built a dedicated runtime for
MixFold from scratch to implement fully static integer quan-
tization, while reusing some operators, such as FlashAt-
tention (Dao et al., 2022), from the llama.cpp Hexagon
backend. All latencies are measured on a mobile equipped
with the Qualcomm Hexagon NPU of a Snapdragon 8 Elite
Gen 5 (SM8850, Hexagon v81). We mainly use Qwen3
family models for evaluation: Qwen3-0.6B, 1.7B, 4B, and
8B (4B is an instruct model). Kernel evaluations cover four
projection shapes from Qwen3 decoder layers: QKV, O,
Up/Gate, and Down projections. We quantize the models us-
ing integer 16-bit activations (A16) and per-channel integer
weights: uniform precision W4-, W3-, W2-, and W2-SEQ-
A16, as well as mixed-precision profiles (MP-A16) with
an output-channel-group size of T = 32. We also apply
PrefixQuant (Chen et al., 2026) to reduce the activation
quantization error caused by the wide activation ranges of
prefix tokens (Section E.1). FlashAttention is excluded from
integer quantization and uses an FP16 KV cache.
End-to-end metrics.
We report decode (tg128, 128 gen-
erated tokens) throughput in tokens per second on the NPU.
Accuracy of the quantized models is measured using GPU
simulation with Qualcomm AIMET (Siddegowda et al.,
2022), because running the full benchmark suite on the NPU
is prohibitively time-consuming. We validate the simulation

Decode kernel latency.

Mixed Precision Model Accuracy
Figure 7 demonstrates the importance of both allocation

precision profiles of Qwen3-4B. As shown in the left panel,
finer-grained allocation pushes the accuracy–BPW Pareto
frontier outward. Specifically, output-channel-group-wise
allocation consistently outperforms layer-wise allocation,
with a larger accuracy gain at lower BPW. Enriching the
bitwidth palette further improves the accuracy–BPW Pareto
frontier (see the right panel). Replacing W2 with the sym-
metric W2-SEQ format improves accuracy at the same BPW,
and adding W3 provides an additional gain. The gain from
adding W2-SEQ to the palette grows at lower BPW, as Pare-

these non-native formats improve accuracy at a given BPW
without sacrificing decode throughput.
5.5
End-to-End Accuracy and Efficiency
Baseline.
We evaluate Q2 K, Q3 K S, Q3 K M, and
Q4 0 using the llama.cpp Hexagon backend (build b11444),
where the first three are sub-4-bit formats and Q4 0 is a
near-4-bit format. We match each MP-A16 profile’s target
BPW to the corresponding sub-4-bit llama.cpp baseline.
Protocol.
Following llama-bench practice (The ggml au-
thors, 2023), we repeat five thermally controlled runs and
report the median (see Section C.2 for details).
Decode throughput.
As shown in the left panel of Fig-
ure 8, MixFold achieves higher decode throughput than
the corresponding llama.cpp baselines at matched BPW
across all model sizes. Moreover, the decode throughput
of MixFold increases as BPW decreases. This contrasts
with llama.cpp, where sub-4-bit formats offer only limited
speedups over Q4 0. For example, Q2 K uses only 65% of
the weight storage of Q4 0 but achieves just 1.03–1.09×
the decode throughput of Q4 0.
Energy efficiency.
Figure 8 (middle) compares decode
energy efficiency during tg128, measured in tokens per joule
(J): a higher value indicates lower energy consumption per
generated token. We measure the power consumption of
the entire system, including the CPU, NPU, and memory,
throughout each run. At matched BPW, MixFold achieves
1.5–4.3× higher energy efficiency than llama.cpp.
Accuracy–throughput optimality.
For this evaluation,
we quantize the weights according to each MP profile using
FlexRound (Lee et al., 2023), replacing the GPTQ-based
quantization used in Figure 7. FlexRound helps compen-
sate for the accuracy loss caused by the coarser per-channel
quantization used by MixFold, compared with the group-
wise quantization used by llama.cpp. As shown in the right
panel of Figure 8, MixFold achieves competitive model ac-
curacy to llama.cpp at matched BPW (from -0.4 to +10.4).
Moreover, MixFold achieves accuracy–throughput Pareto
optimality. These results suggest that, despite using coarser
per-channel quantization, MixFold can achieve compara-
ble or higher accuracy to llama.cpp at matched BPW by
combining fine-grained mixed precision with an appropriate
PTQ method, while maintaining high runtime efficiency.

RELATED WORK
Executing low-bit weights.
On GPUs, weight-only quan-
tizers such as GPTQ and AWQ dequantize weights to FP16
before the GEMM (Frantar et al., 2022; Lin et al., 2024), and
later kernels hide that cost behind the tensor cores (Frantar
et al., 2025; Xia et al., 2024; Zeng et al., 2025) or fold it into
table lookups (Park et al., 2024; Guo et al., 2024). Atom and
QServe keep the arithmetic in integers but at the bitwidths
the tensor cores provide (Zhao et al., 2024; Lin et al., 2025).
On CPUs, T-MAC and bitnet.cpp replace the multiplication
with table lookups (Wei et al., 2025a; Wang et al., 2025).
On mobile NPUs, the llama.cpp Hexagon backend converts
packed weights to FP16 before the MMA (The ggml authors,
2023). llm.npu keeps the NPU on its native INT8 path for
prefill and runs decode on the CPU (Xu et al., 2025), and
PowerInfer-2 splits decode between the NPU and the CPU
by activation density (Xue et al., 2024). MobileQuant and
Quant.npu adapt the quantizer to the NPU’s integer arith-
metic but stay at 4 bits or above (Tan et al., 2024; Zhang
et al., 2026). T-MAN multiplies low-bit weights by table
lookup on the NPU’s vector cores, which frees it from na-
tive datatypes but leaves the matrix unit idle at decode (Wei
et al., 2025b). We compare its kernel with ours in Sec-
tion 5.2. Hao et al. (2026) expose the NPU’s tile shape to
the quantizer. ParetoQ shows that the symmetric W2-SEQ
grid is more accurate than the two’s-complement grid, but
gives no way to execute it (Liu et al., 2025). MixFold neither
converts weights nor leaves the matrix unit idle: W2-SEQ
and W3 run as native integer MMA, and the vector unit
never converts weights at decode.
Mixed-precision allocation.
Mixed precision trades al-
location granularity against hardware fit. HAWQ and its
successors assign a bitwidth per layer from Hessian sensitiv-
ity, and HAWQ-V3 solves the assignment as an ILP (Dong
et al., 2019; 2020; Yao et al., 2021). HAQ learns the as-
signment from measured latency (Wang et al., 2019), and
differentiable relaxations search it by gradient (Wu et al.,
2018; Yang & Jin, 2021); both decide per layer. For LLMs,
SqueezeLLM, SpQR, and OWQ keep sensitive weights or
columns at a higher precision (Kim et al., 2024; Dettmers
et al., 2023; Lee et al., 2024), SliM-LLM allocates per group
by salience (Huang et al., 2024), MixLLM allocates per out-
put channel (Zheng et al., 2026), and GAMMA learns a
global allocation under a bit budget (Yao et al., 2026). Mix-
Fold admits the non-native W2-SEQ and W3 into the palette
and adopts hardware-aware finer granularity to move the
accuracy–throughput frontier outward.
7
CONCLUSION
We presented MixFold, which runs sub-4-bit and mixed-
precision LLM weights on a mobile NPU without native low-
bit support. It executes W2-SEQ and W3 on native integer
MMA without converting the weights, and combines them
with hardware-aware output-channel group-wise mixed pre-
cision. On the Qualcomm Hexagon NPU of a Snapdragon 8
Elite Gen 5 (SM8850, Hexagon v81), MixFold moves the
accuracy–throughput frontier beyond llama.cpp’s sub-4-bit
formats while improving power efficiency. All these gains
follow from nativeness: no weight is converted before the
matrix unit, so decode is bound by weight bytes and the
arithmetic stays in integers. Hexagon is a representative
case rather than a special one. Mobile NPUs keep few na-
tive datatypes to save area and power, so sub-4-bit formats
are non-native on most of them. MixFold needs only native
2-bit integer MMA, per-channel requantization with a bias
set at run time, and a vector unit that shares on-chip memory
with the matrix unit. NPUs with these features can adopt
the same execution paths.

A
LIMITATIONS
Effectiveness in single-thread vector unit.
The perfor-
mance advantage of our fold methods is established against
single-thread weight expansion. In this setting, the vector
unit converts unsupported weight formats before the ma-
trix unit can consume them, and this conversion can lie on
the critical path. Folding removes the expansion stage and
allows the reduced weight traffic to translate into lower la-
tency. However, processing throughput increase by multiple
vector threads can reduce the conversion time and narrow
or eliminate this advantage.
Unverified end-to-end gains for multi-row decoding.
Our end-to-end evaluation covers single-stream autoregres-
sive decoding at M = 1. We have not verified the end-
to-end effectiveness of MixFold for M > 1 decoding, in-
cluding speculative decoding and concurrent decoding of
multiple sequences. Evaluating the fold paths and mixed-
precision profiles within these workloads remains future
work.

B.2
W3 Plane Packing
A W3 code with bits c2c1c0 is stored as the raw W2 code
(c2 ≪1) | c1 and the raw W1 code c0. The W2 raw code is
interpreted as signed two’s complement by the native HMX
kernel, so raw codes 0, 1, 2, and 3 represent 0, 1, −2, and
−1, respectively. The W1 plane is unsigned. HMX reads
the W2 plane in its signed 2-bit weight mode and the W1
plane in its unsigned 1-bit weight mode, so neither plane is
widened. All W2 tiles are stored first and all W1 tiles second.

B.4

The output-correction form (Section B.1) costs an HVX
pass over all M × N outputs and a headroom in which
large corrections are clipped. The bias-fold avoids both at
M = 1 because the single row sum R1 can enter the per-
channel input bias. For M > 1 the correction differs per row
and cannot enter a per-channel bias. The accumulator-fold
instead lets the HMX accumulation add it through correction
columns appended to both operands.

Filling the correction columns.
Activation entries are

entries of a row sum to Lm exactly, each one is a valid code,
and each lies within one of 2q−1 −1 + ⌊(Rm −c)/(2S)⌋,

the middle of the code range plus the row’s half-deviation

constant +1 weight tiles into VTCM, and folds Rc into the
input bias of every output channel. HMX appends the E
correction-column tile pairs to the accumulation of each
output tile, so an output tile takes K/T + E tile products
instead of K/T: for E = 1, 3% more HMX work at K =
1024 and 0.8% at K = 4096.
Latency.
The accumulator-fold is the default W2-SEQ
path for 2 ≤M ≤32, for homogeneous W2-SEQ and
for the W2-SEQ groups of mixed kernels. Across the 12
projection shapes and M ∈{2, 4, 8, 16, 32} it stays within
1% of the native W2 kernel up to M = 8 on Qwen3-4B
and 8B (at most 23% above it, on the smallest Qwen3-0.6B
shapes from M = 8 on).

C
MEASUREMENT METHODOLOGY
C.1
Kernel Measurement Protocol
Each kernel latency in Sections 5.2 and 5.3 and Section D
is the median over two to five device processes, run in
randomized order over all kernels of a measurement set.
Each process allocates the weights in the deployed layout,
warms up once, and averages 32 repetitions. A mixed kernel
repeats a fixed pattern of formats over its 32-channel groups
(e.g., W2-SEQ, W3, W4, W4), and its BPW is the mean of
the pattern.
C.2
End-to-End Measurement Protocol
Both runtimes are measured on the same phone with the
procedure of llama.cpp’s llama-bench. Each run is a
fresh process that loads the model, runs one warm-up pass
(a prompt and one generated token), and then five repetitions
of one workload: tg128 (128 generated tokens), pp512 (a
512-token prompt), or pp512+tg128 (both). The run value
is the mean tokens per second of the five repetitions. Every
configuration and workload runs five times, and the configu-
rations take turns. A run starts only when the hottest CPU
and NPU sensor is within 10 ◦C of its idle temperature. We
report the median of the five runs. Their spread (maximum
minus minimum over the median) is at most 3.6% for Mix-
Fold and 7.5% for llama.cpp. The llama.cpp runs use the
same procedure in separate sessions on the same phone.
Models.
Latencies use latency-equivalent models whose
weights are random but whose byte layout and metadata
match the exported checkpoints. The group pattern of every
synthetic MP profile follows the statistics of the real Qwen3-
0.6B MP3.4 profile. The real Qwen3-4B W3 and Qwen3-
0.6B W4 checkpoints run within 0.2% of their latency-
equivalent models at tg128, and the real Qwen3-0.6B MP3.4
checkpoint within 2% for all three workloads.
Power.
Energy is measured on a development device with
the same SoC, whose power monitors cover every rail. The
sum of all rails is sampled at 10 Hz over each run, with the
screen off and no other process running, and idle power is
not subtracted. Energy is the integrated power over a run
divided by its generated tokens (end to end) or kernel calls
(kernels), and we report the median of five runs.
C.3
llama.cpp Baselines
The llama.cpp rows use publicly released GGUF files (Ta-
ble 6). All of them were quantized with an importance
matrix computed by the publisher on its own calibration
text: Unsloth’s for every file except the Qwen3-8B Q4 0,
which Unsloth does not release and which comes from bar-
towski. The throughput runs for Qwen3-4B-Instruct-2507
use the unsloth/Qwen3-4B-GGUF files of the same for-
mats, which match its GGUFs tensor by tensor in type and
size. The k-quant presets keep some projections at higher
precision: Q2 K stores the value, output, and down projec-
tions in Q3 K or Q4 K, so its decoder linear weights average
2.93–2.96 BPW rather than the 2.63 BPW of a Q2 K block.
We place llama.cpp at this decoder-linear BPW, the same
population of weights our BPW counts. Token embeddings
and the LM head are excluded on both sides. Our BPW
counts the weight codes. The per-group requantization pa-
rameters and the extra data of the W2-SEQ and W3 decode
paths add 0.03–0.12 BPW on Qwen3-4B and 8B and up to
about 0.3 BPW on 0.6B (Table 9), whereas the GGUF BPW
includes the block scales.

T-MAN stores one bit-serial copy of the weights (asymmet-
ric, group size 64, 2.5 BPW at 2 bits) and has two kernel
paths. Its public LUT kernel (precompute, linear, and final-

while each weight chunk is streamed into VTCM once. Its
path for M > 1 is not public, so we implement it as its
paper describes on the DMA pipeline and thread pool of
llama.cpp’s Hexagon backend. HVX repacks each bit-serial
weight chunk to bit-parallel and converts it to FP16 with
a two-level LUT, and HMX multiplies in FP16, pipelined
with the DMA. Both paths match a CPU reference on every
Qwen3 projection shape. Table 14 takes the faster path per
projection and M, which is the LUT kernel up to M = 4
