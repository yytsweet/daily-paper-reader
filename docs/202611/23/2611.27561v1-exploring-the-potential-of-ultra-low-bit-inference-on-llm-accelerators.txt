Abstract—Vector quantization (VQ) enables ultra-low-bit com-
pression of large language models (LLMs) by encoding groups
of values as compact codebook indexes. However, reconstruct-
ing these values for computation requires frequent codebook
lookups, which conflict with the dataflows of conventional LLM
accelerators and limit the performance gains from VQ com-
pression. Consequently, prior work has resorted to VQ-specific
accelerator designs, which either incur substantial additional
hardware overhead or support only a limited range of inference
scenarios. In this work, we argue that existing systolic-array-
based LLM accelerators already possess the essential hardware
resources for efficient VQ inference, but lack the mechanisms
to effectively exploit them. To bridge this gap, we present
VQACC, an architectural enhancement that jointly redesigns
the existing operand buffer’s access logic and data mapping
to reuse its storage and port resources for codebook lookups,
seamlessly integrating dequantization into the normal operand-
addressing dataflow. Evaluation shows that VQACC achieves a
2.63× speedup over the EVA baseline, with additional hardware
occupying only 0.17% of the compute array’s area.
Index Terms—vector quantization, large language model, de-
quantization, systolic array.
I. INTRODUCTION
The success of large language models (LLMs) in language
understanding and generation places increasing demands on
hardware memory capacity and bandwidth [14], [18], [22],
[37]. LLM inference stores large model weights and key–value
(KV) caches that retain information from previously processed
tokens. KV caches grow with context length and the number
of concurrent requests, and both weights and KV caches must
be accessed repeatedly during token generation. Quantization
represents these data with fewer bits, reducing transfers and
allowing larger models and longer contexts within a given
memory budget [9], [11]–[13], [23].
Vector quantization (VQ) extends this opportunity to ultra-
low-bit inference with 4-bit or lower precision per value. Un-
like commonly used element-wise quantization, which com-
presses each value independently, VQ jointly represents a
group of values as a vector. It learns a shared codebook of rep-
resentative vectors and replaces each original vector with the
low-bit index of its closest representative (Fig. 1(a)). The index
thus encodes the pattern across multiple elements, exploiting
their correlations to preserve information that independent
quantization loses. For LLMs, VQ can achieve higher accuracy

However, a gap remains between VQ’s strong compression

problem at the cost of additional hardware or limited appli-

transformation, but supports VQ only for model weights, with
benefits concentrated in small-batch LLM decoding [7].
This work starts from a key observation: in existing LLM
accelerators based on systolic arrays (SAs), operand-buffer ad-
dressing is naturally compatible with codebook lookup, and its
capacity and ports can also support storing multiple codebooks
of typical size and performing parallel, conflict-free lookups.
What is missing is a mechanism to exploit these resources
effectively. We therefore propose VQACC, a VQ-enhanced
architecture built on existing SA-based LLM accelerators.

II. BACKGROUND AND RELATED WORK
A. Quantization in LLM Inference
LLM inference consists of a prefill phase and a decoding
phase. Prefill processes the entire prompt at once, whereas de-
coding generates one token at a time. Weights and KV caches
are fetched repeatedly for each generated token with little
reuse, so decoding is typically bound by memory bandwidth.
Batching multiple requests amortizes weight fetches across the
batch, but each request keeps its own KV cache, so KV traffic
still grows with both the batch size and the context length.
KV caches also occupy memory capacity in proportion to
these two factors, limiting the number of concurrent requests
and thus the benefit of batching [1], [4]. Memory bandwidth
therefore remains a severe challenge for LLM decoding.
Quantization stores weights and KV caches in fewer bits,
reducing both memory traffic and footprint and thereby deliv-
ering significant speedups in LLM decoding [28], [35]. The
same quantized weights usually serve prefill as well, because
keeping a separate high-precision copy for prefill would offset
the memory savings, which memory-constrained inference
systems cannot afford [31], [36].

at the cost of expensive dequantization: on existing commer-

regular LLM dataflows handle its frequent codebook lookups
poorly, causing heavy on-chip data movement and bank con-
flicts, so VQ can even run slower than FP16 (Fig. 2(c)).
C. VQ-Based LLM Accelerators
Several accelerators customized for VQ-based LLMs have
been proposed to overcome the inefficiency of dequantization,
but they either incur substantial hardware overhead or support
only a limited range of inference scenarios.
Vortex introduces dedicated hardware for VQ dequantiza-
tion [27]. An additional multi-bank codebook buffer holds
multiple codebook copies to support parallel, conflict-free
lookups, and an additional lookup staging buffer reorders and
aligns the lookup results before they enter the compute array.
These additional buffers, however, incur expensive hardware
overhead.
EVA instead avoids weight dequantization by moving the
lookup to the output side [7]. It multiplies the activations with
the weight codebook, treats the products held in the output
buffer as a table of partial sums, and reuses the multiple
banks of the output buffer to select and accumulate table
entries in parallel according to the weight indexes. Because
both the table and the number of lookups grow with the
batch size, EVA’s benefits concentrate in small-batch decoding.
Moreover, the transformation depends on how a weight tensor
is partitioned into blocks that share one codebook, which
restricts it to weight VQ.

III. VQACC DESIGN
A. Overview
In this section, we present VQACC, an architectural en-
hancement that accelerates VQ dequantization by efficiently
reusing the resources that an LLM accelerator already pro-
vides. Fig. 3 shows the overall architecture of VQACC.
VQACC builds on typical SA-based accelerator architec-
tures [5], [10], [17]: the SA reads activations from the activa-
tion buffer (AB) and weights or KV caches from the weight
buffer (WB), and writes results to the output buffer (OB);
a vector processing unit (VPU) with its register file (VRF)
executes operators other than matrix multiplication; and an
L1 cache or shared buffer passes VPU results to the SA
on chip, as kernels such as FlashAttention require [6], [18].
AB, WB, and OB are built from multi-bank SRAMs, each
bank with two read/write ports, which supports ping-pong
scheduling between external data transfers and operand supply
to the SA. On this basis, VQACC enhances only the operand
path from WB to the SA so that it can additionally support
the VQ dequantization flow. Four designs realize this change,
numbered ①–④in Fig. 3 and detailed in Sec. III-B–III-E.
B. Codebook-Index Mapping
First, we propose a codebook-index mapping that stores
codebooks and indexes in WB’s existing banks in a layout that
enables efficient lookups. We assume that WB holds 64 KiB
in 32 dual-port banks of 16-bit width for FP16 operands.
As Fig. 4(a) shows, VQACC splits each 32 KiB ping-pong
half of WB into 16 KiB of indexes and 16 KiB of codebooks.
While the SA consumes the active half, the idle half receives
the indexes and codebooks of the next tile. Based on the
target codebook configuration introduced in Sec. II-B, both
regions meet their storage requirements with the capacity WB
already has. For the index region, 16 KiB of indexes can
decode into 64 KiB of FP16 values even at d = 2, twice the
32 KiB capacity limit of an unquantized half. Any unquantized
operand tile that fits in a half therefore still fits in the index
region after VQ. For the codebook region, VQACC maps
32/d codebooks (copies of the same codebook or different
codebooks), which exactly fill the 16 KiB codebook region,
as a 256-entry FP16 codebook occupies 512d B. For the

C. Index Address Generator and Port Multiplexing
Second, we use an index address generator together with
a port multiplexing strategy that provides, at the same time,
the bandwidth a lookup needs for its index input and for its
output. VQACC first provides one port of each of the 32
banks as a read port that outputs codebook lookup results.
Among the remaining ports, we choose eight adjacent banks
to provide read ports that fetch 8 × 16 bits, i.e., 128 bits of
indexes as the input to the codebook lookup. Because a 128-
bit index word holds sixteen 8-bit indexes, one word covers
all 32/d codebooks even at d = 2, so the indexes read in one
cycle guarantee that every codebook is supplied at least once.
These eight adjacent banks are therefore defined as an index
window: we divide the 32 banks into four windows and use a
4:1 multiplexer to move the window across the 32 banks. We
add an index address generator that turns each 128-bit index
word into 32 index addresses, one per bank, and drives the
lookup read ports of the banks in the next cycle. Finally, the
remaining 24 banks provide write ports that write the indexes
of the next tile into the idle half, along with new codebooks
when the codebooks need to be replaced.
This port multiplexing sustains the full operand bandwidth
of the SA with little index traffic. The read ports of the 32
banks return 32 FP16 values per cycle, exactly the number
of operands the SA consumes, so the SA is fed at the same
rate as with unquantized FP16 operands. Meanwhile, each

D. Shift Layout Unit
Third, we design a lightweight shift layout unit that converts
WB’s lookup results on the fly into the operand layout the SA
consumes. The unit works together with the output-stationary
SA; we explain it with the example in Fig. 5, which uses
B = 8 WB banks for clarity and extends directly to B = 32.
As Fig. 5(a) shows, each SA column receives one operand
per cycle and starts one cycle after its left neighbor, forming a
diagonal wavefront: in cycle t, column c consumes the operand
at reduction position k = t −c. Because VQ vectors usually
lie along the reduction dimension, the elements of looked-
up vectors must enter the same SA column over consecutive
cycles. To enable parallel, conflict-free lookups, however, the
d elements of each codebook vector are spread over d separate
banks, so a lookup returns them side by side, and the results
must be transposed before they can flow down the SA columns
(red boxes in Fig. 5(a)).
To solve this efficiently, we design a shift-based transpose
built on reverse placement, which folds the layout alignment
into the SA’s operand supply. First, VQACC spreads the
reduction dimension across all B banks in reverse order: from
the SA’s view, the operand element at reduction position k is
stored in bank b = B −1 −(k mod B) (Fig. 5(b)). Within
a codebook, each vector is stored in reverse, e.g., elements
0–3 of CB0 in banks 7–4. Some VQ algorithms, such as CQ
for key cache [34], use different codebooks for consecutive
vectors along the reduction dimension, so one reduction span
is restored from several codebooks; the order across codebooks
is therefore reversed as well, as CB0 occupies banks 7–4
and CB1 banks 3–0 in the example. Next, we derive which
bank feeds which SA column. In cycle t, column c needs
position k = t −c, which reverse placement puts in bank
b ≡B −1 −t + c (mod B), so the distance from this target
bank to the column is c −b ≡t + 1 (mod B), independent
of the column. Each bank therefore reads its data at the index
addresses that produce the diagonal wavefront of Fig. 5(a),

E. Codebook-Stationary Dataflow
Finally, we design a codebook-stationary dataflow at tile
granularity that keeps each codebook resident in WB for as
long as possible, so that codebook loads cost less. As Fig. 6
shows, VQ algorithms often partition an operand into regions
that each use their own codebook. A conventional dataflow
schedules tiles without regard to these regions, so a single
tile frequently crosses codebook boundaries; every crossing
reloads a codebook, consuming DRAM and L1 bandwidth and
stalling the lookups that depend on it. Let TD be the tile size
along D in the conventional dataflow and T ′
D the tile size that
VQACC uses instead. When CD > B (bank number of WB),
VQACC sets T ′
D = min(TD, CD) so that no tile straddles
two codebook regions. When CD ≤B, VQACC sets T ′
D =
nCD with the largest positive integer n satisfying nCD ≤B,
as the codebook mapping of Sec. III-B can hold and decode
different codebooks simultaneously; a tile thus grows as large
as the lookup bandwidth allows. Furthermore, while keeping
the operand and result residency of the conventional dataflow,

IV. EVALUATION
A. Experimental Setup
We evaluate Llama-2-7B [29], Qwen3-8B [24], and Mistral-
7B [16] under the VQ configurations in Table II, using
AQLM-1 (W1) [8] and GPTVQ-2 (W2) [30] for weights
and CQ-2 (KV2) and CQ-4 (KV4) [34] for KV caches. The
overall comparison combines them into W1KV2, W2KV2, and
W2KV4 and covers decoding with batch sizes 1–32 and a 2K-
token KV cache.
Building on SCALE-Sim [25], [26], we develop a cycle-
level simulator for VQ LLM inference, with the architecture
parameters in Table III. We compare VQACC with four
designs built on the same accelerator configuration. Full FP16
uses full FP16 operands. VPU Dequant dequantizes in the
VPU; we extend the VPU with VQ-specific instructions so
that it performs conflict-free lookups from the VRF at the
same lookup bandwidth as VQACC. Its gap therefore lies
mainly in the extra on-chip traffic of writing the reconstructed
FP16 operands back to WB through L1. EVA-OL32 follows
EVA [7] and reuses 32 output-buffer banks for output lookup;
it keeps KV caches in FP16 and does not support prefill.
Vortex-IL uses the dedicated dequantization pipeline of Vor-
tex [27] to look up operands on the input side, with additional
2 × 16 KiB ping-pong codebook buffers and 2 × 8 KiB ping-
pong lookup staging buffers. Vortex additionally integrates an
EVA-style mechanism that is compatible with this pipeline and
selects between the two according to which suits the scenario;
since EVA is already part of our comparison and VQACC
can incorporate EVA equally cheaply, we do not evaluate that
mechanism separately. Moreover, we do not perform online
VQ (clustering) of the dynamically generated KV caches on
any of these designs; as in common VQ deployments, it is
offloaded to an off-chip processor [33] and does not affect
LLM inference. We implement VQACC and the baseline
designs in SystemVerilog and synthesize them in 28 nm at
1 GHz to compare area. SRAM buffer areas come from a
commercial memory compiler and SRAM access energy from
CACTI [3]; DRAM energy uses the DDR4 access energy
reported in GANAX [32].
B. Decoding Performance
Across all models, VQ algorithms, and decoding config-
urations, VQACC is the fastest design on average (Fig. 7).
Relative to Full FP16, VPU Dequant, EVA-OL32, and Vortex-
IL, it delivers average speedups of 1.79×, 1.71×, 2.63×,
and 1.10×, respectively. That Full FP16 and VPU Dequant
differ by only a few percent shows that optimizing the lookup
operation alone cannot solve the VQ dequantization bottle-
neck: once VQ compression removes most of the DRAM
accesses, overall performance becomes limited by on-chip
execution time, so the additional on-chip traffic produced by
dequantization is an equally significant cost. Although Vortex-
IL builds a dedicated dequantization pipeline that optimizes

E. Codebook-Stationary Dataflow
Fig. 13 compares the conventional and codebook-stationary
dataflows on VQACC. In the attention computation, the con-
ventional dataflow switches codebooks frequently, and the
small SA compute tiles (Sec. IV-B) cannot hide that latency,
so it incurs 5.4–5.8× the latency and 5.3–6.1× the energy of
the codebook-stationary dataflow. In the FFN, W2’s large CK
and CN give large tiles that hide the switches, so the latency
gain is small, yet 8× fewer codebook loads still lower FFN
energy by 29% on average.
V. CONCLUSION
Vector quantization is a key enabler of ultra-low-bit LLM
inference, yet its dequantization flow is a significant per-
formance bottleneck. This paper presented VQACC, which
6


unlocks efficient VQ inference on existing SA-based LLM
accelerators. VQACC adds no separate dequantization stage;
instead, it reuses the storage, ports, and addressing of the
existing weight buffer, so that codebook lookups are folded
into ordinary operand reads. It achieves overall speedups of
2.63× and 1.10× over the existing VQ LLM accelerators EVA
and Vortex, and occupies only 0.17% of the compute array’s
area.
