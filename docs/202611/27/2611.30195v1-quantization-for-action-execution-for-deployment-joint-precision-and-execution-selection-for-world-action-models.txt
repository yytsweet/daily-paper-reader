# Abstract 

World action models guide robots by predicting the effects of actions or generating commands from observations. A model may compare hundreds of candidate futures before acting, repeatedly reading weights that must fit in device memory. Post-training quantization reduces the number of bits used to store pretrained weights, but a smaller model is not necessar-ily a deployable one: temporary tensors can exceed graphics processing unit (GPU) memory limits, while even small pre-diction errors can change the selected action. This creates two coupled challenges: identifying bit assignments that pre-serve task performance and determining which of them meet real execution constraints, without exhausting costly task trials. We present PTQ4WAM , a framework for choosing layer-wise bit assignments and execution routes under mem-ory, latency and task-evaluation budgets. Calibration mea-surements guide candidate proposals, optionally with a lan-guage model agent. We profile full-model routes on the GPU before spending task trials on feasible assignments. Fusing group rescaling and reading visual history in place can make an otherwise infeasible assignment deployable. Across 15 workloads from four model families, the median task score is 99.2% of the corresponding 32-bit floating-point (FP32) score. On fixed GPU replays, the median speedup over FP32 is 2.36 × and the median reduction in peak allocated memory is 71.5%. The code will be released soon. 

# 1. Introduction 

A robot choosing its next move can predict where several ac-tions would take it, then execute the one that brings it closest to its goal. DINO-WM and LeWorldModel (LeWM) make these predictions in a learned visual feature space [19, 33]. V-JEPA 2-AC plans with a predictor built on pretrained video features [3]. Fast-WAM uses video and action supervision to generate commands directly [31]. These world action models (WAMs) must fit alongside the observations and in-termediate features they process. A predictive planner also uses the same weights repeatedly. In one physical robot setup, V-JEPA 2-AC uses a 300M-parameter predictor and compares 800 action candidates in each of ten refinements. Choosing one action takes 16 seconds on an RTX 4090 [3]. An onboard controller must meet a memory budget as well as a deadline for choosing its next action. Post-training quantization (PTQ) offers a way to shrink a pretrained WAM without collecting new robot interactions for retraining. Fewer bits per weight reduce the size of the saved model and the data its operators must read on each call. With a fixed storage budget, keeping more bits in one set of layers leaves fewer for the rest. With only a few task evaluations, how can we find an assignment that preserves control performance and runs within the device limits? 

Task alignment. Consider two candidate trajectories whose predicted endpoints lie at nearly the same distance from the goal. A small feature error can swap their order and change the action. A larger shift that moves both predictions together can leave the decision intact. This makes average reconstruction error an unreliable guide to which layers need more bits. Action sensitivity and rollout feedback already guide quantization in recent WAMs [1, 27, 34]. To choose a whole model, we need to know how its precision choices work together when the original planner or controller acts. 

Feedback cost. Representative inputs used for calibration can reveal numerical errors in many layers in a single pass. Testing a complete assignment for control success can re-quire running the controller from many initial states until each trial ends. Runtime feasibility. Assignments of the same saved size can differ in whether they fit during prediction. A quantized layer may write a temporary result before rescaling it. Attention over past observations may first copy the history into a new tensor. The peak depends on which of these tensors coexist with the rest of the model. An individual kernel’s speed or the size of the weight file cannot tell us whether the complete call will finish within both the memory and time limits. A trial spent on an infeasible model leaves one fewer chance to test a model the device could use. PTQ4WAM first measures which bit assignments the de-vice can run, then uses limited task evaluations to choose the best-performing model and its GPU implementation. Read-ing history in place, for example, can qualify a model that exceeds the memory limit when its history is copied. The map can then enter the task comparison in Figure 1(a). Fig-ure 1(b) shows how the planner uses the selected model. • Device-constrained precision selection. We use the orig-inal task score to compare whole-model bit assignments. Each assignment is tested and saved with the GPU kernels that meet the device’s memory and time limits. • Calibration-guided proposals. We can use a large lan-guage model (LLM) agent with model structure and cal-ibration measurements to propose a small set of assign-ments. A deterministic generator checks them before the planner or controller spends time scoring them. • Low-memory execution. We rescale outputs inside the low-bit operator and read past visual features directly from their existing buffers. We time a full call and measure its memory to find the routes that meet both limits. 

# 2. Related Work 

How to choose the bit width. Prior work calibrates blocks, uses curvature to choose weights or bit widths, and adjusts ac-tivation ranges for groups of tokens [7, 8, 15, 16]. AdaRound learns how to round weights, QDrop varies which activations are quantized, and Q-BERT and PTQ4ViT use curvature in-formation [20, 24, 28, 32]. The loss on a task or its sensitivity can guide which parts of a model to protect [1, 21, 25, 27, 30]. QuantWAMs uses rollout feedback to protect selected de-noising steps [34]. Errors from several components can change a planner’s decision [10]. A local score may thus rank two complete models in the wrong order. We test each map on the task once it meets both device limits. 

How to use calibration data. Calibration can redistribute outliers through rescaling or learned transformations [17, 23, 29], rotate activations [2, 18], or preserve outliers in a low-rank branch [14]. Device measurements can guide bit allocation [26]. In constrained Bayesian optimization (BO), results from previous trials guide the next choice [11]. A single trial may require many predictions before success is known. Our optional LLM uses calibration data to propose distinct maps before the first trial. We spend the available trials only on maps that meet both device limits. 

How to reduce memory use. Tensor compilers and kernel libraries fuse operations or tile matrix products [4, 5, 22]. Marlin and FLUTE reduce the cost of low-bit matrix products [9, 12]. Attention kernels reduce temporary storage or read separate memory blocks [6, 13]. Removing a buffer saves little at the model level if a different operator sets the peak. We profile each full call with fused rescaling or direct history reads to see which maps fit within both limits. 3. Method 

We start with a pretrained WAM and its original planner or controller. A task specifies what the robot should do and how we score it. For example, a push succeeds when the object reaches its goal. A workload w specifies the model, input shapes, history length and planning horizon for that task. A precision map c assigns a weight bit width to each eligible component. An execution route r specifies the GPU operations used to run that map. Every route executes the same stored weights with the same quantization parameters. Calibration inputs set the quantization scales, guide can-didate proposals and supply the shapes and features for pro-filing. We choose among models on development outcomes and evaluate the choice on held-out data. Each source is a planning instance, a recorded trajectory or a controller run from its initial state to termination. We assign a whole source, including every frame and outcome, to a single split.

Testing an assignment with Equation (3) requires more than a forward pass. In control the first action determines the next observation, so the task evaluator must follow the resulting trajectory. We use information available during calibration to decide which maps warrant this expense. 

Build a pool of legal maps. Swapping the bit widths of equally sized components moves precision within the model while preserving the total number of weight bits. In the joint-search experiment, we start from several maps at the same storage target. More swaps move precision farther from the starting map. 3.3. Low-Memory Execution 

Fused group rescaling (FGR) and direct history reads (DHR) preserve the task output. Figure 2(a) traces a partial sum through a linear layer, and Figure 2(b) shows where the consumer reads past and current features. 

Fused group rescaling. A quantized linear layer forms one integer partial dot product pijg for each group g of input channels, output row i and output channel j. A separate rescaling operator requires these intermediate values to be written to device memory and read back. FGR rescales each partial where it is computed. With activation scale saig ,weight scale swjg and bias βj , the operator writes a single value yij for that row and output channel, given by 

yij = X

> g

saig swjg pijg + βj . (7) The scales can differ across groups, so rescaling precedes summation. The kernel adds the bias and converts the output to its prescribed format before the final write. The reference for this calculation is the linear layer with the same quantized codes, groups and zero points. Each integer partial must fit its accumulator. If these conditions hold, moving the scale multiplication into the producer pre-serves the operator in real arithmetic. Changing the order of floating-point additions can still change a rounded output. We therefore check agreement with the quantized reference before a fused route can enter the search. 

Direct history reads. A predictor may keep past features and the latest observation in separate tensors. Let X denote their logical concatenation. Segment Xj ends at exclusive offset oj , with o0 = 0 . Instead of copying the segments to a new buffer, DHR finds the segment that owns position p and reads the element in its own segment, 

X[p] = Xj [p − oj−1], oj−1 ≤ p < o j . (8) Attention preserves the original positions and masks and uses one normalization over the entire history. Normalizing each segment separately would change the relative weight of past and current observations. A direct read is valid while both segments remain immutable and the consumer uses their values and logical positions. A consumer that writes through its input or requires a contiguous address range retains the copy. Both segments must remain in memory until the consumer has finished reading them. 

Check the peak for the full prediction. FGR can require workspace, and DHR keeps its input segments live until their last use. Let A be the original allocation at the changed stage, dsave the net bytes saved there, and C the largest allocation at any unchanged stage. The change reduces the peak by the following number of bytes, 

∆Mpeak = max( A, C ) − max( A − dsave , C ). (9) When another stage sets the peak, removing more bytes at the changed stage can still save traffic while leaving the peak unchanged. We therefore measure the entire call for each route before applying the limits in Equation (2).

4.1. Deployment across 15 Workloads 

All four families run faster and use less GPU memory on the fixed inputs (Table 1). Task scores remain close to FP32 on most workloads. For Franka Ranking, the decrease corre-sponds to one additional incorrect comparison. Fast-WAM Long and LeWM Wall both benefit from cheaper prediction, yet their control scores move in opposite directions. We next examine which actions each precision assignment preserves. 

From prediction time to control time. On Fast-WAM Long, we timed complete batches of 500 episodes at a fixed horizon, including environment updates, schedul-ing and input/output. Against optimized bfloat16 (BF16), PTQ4WAM reduced the mean batch time from 973.0 to 675.7 s with similar observed success (95.10% and 95.32%). Preparing PTQ4WAM took 3,469.4 s, compared with 48.6 s for BF16. At the measured batch times, the initial cost is recovered in the twelfth batch. The deployment comparison changes both weights and execution. We fix the candidate pool to compare scoring rules and the trial budget to compare proposals. Running the same weights on each route isolates the cost of execution. 

4.2. Device-Constrained Precision Selection 

Which prediction errors change an action? On LeWM Wall, a planner ranks candidate actions by their predicted consequences. A perturbation that reverses the order of the leading actions can change the robot’s path even when the predicted features barely move. We test this explanation by keeping the planner and initial states fixed and replacing quantization error with random noise of matched magnitude. We measure mean squared error in standardized features. We compare the first action against a reference from higher-budget planning or environment labels, then run the con-troller to termination. Table 2 gives the fraction of reference actions recovered and the fraction of trials that succeeded. The reported mean feature error is identical for matched noise and PTQ4WAM. The selected map agrees with the reference action more often and succeeds more often. Re-turning the components ranked most sensitive by calibration to higher precision brings the features closer to their refer-ence values, yet reduces both action agreement and control success. Random restoration controls for the choice of which layers to restore. The map with the lowest feature error need not preserve the action that the planner would choose. Wall shows the largest gain over FP32 in the deployment comparison. To test whether extra tuning trials explain the gain, we gave the FP32 planner 12 development configura-tions and PTQ4WAM 12 assignments. On the same held-out states, the quantized planner still led by 11.07 percentage points. The gain is specific to this checkpoint and task. Across the other deployments, quantization can preserve, raise or lower the overall task score. We also changed the initial states, goals and planning horizon on Wall while retaining the checkpoint. The quan-tized planner had higher success and fewer severe failures in all three comparisons. At 1.5 times the usual horizon, the severe-failure rate fell from 11.6% to 5.2%. This count includes collisions, unsafe terminal states and timeouts. To-gether with the matched-noise control, the result ties the gain to decisions made over a rollout. Several layers change together in this comparison, so we cannot attribute the gain to the rounding of any one weight.

4.3. Calibration-Guided Proposals 

Which candidates merit a trial? We fixed the task-scoring rule and varied the shortlist. Across six equally weighted planning and control tasks, the agent reached 90.93% mean success with 12 candidates, close to 91.00% when all 48 were scored. The strongest alter-native at the same 12-candidate budget, the sensitivity-guided list, reached 90.37%. Random and fixed lists both scored below the sensitivity-guided list. Does testing more candidates always find a better model? In a separate Fast-WAM Long experiment we froze nested pools before collecting any task scores and used the same 384 development outcomes for each pool size. Expanding from 48 to 192 candidates raised the winning development count from 368 to 373. Held-out success was 94.36% and 94.33%, respectively, while preparation grew from about 272 to 1,017 seconds. In this experiment the larger pool offered more chances to fit the development sample. The apparent gain on the development sources disappeared when we ran the selected models on new sources. 

What information guides the shortlist? On Fast-WAM Long, we shuffled calibration statistics among components of compatible shape. The values, model structure and budget of 12 assignments stayed fixed. Omitting the statistics tests their value to the agent. Figure 3 also compares the agent with a deterministic rule given the correct statistics. The best shortlist came from giving the agent measure-ments for the layers that produced them. Shuffling values across layers was worse than withholding them entirely. With the same measurements, the deterministic heuristic also trailed the agent. These gains measure the value of feedback from the shifted task. 5. Conclusion 

Compressing a world action model requires preserving deci-sions under device limits. Similar feature errors can lead to different actions, and smaller weights can still exceed GPU memory or latency limits. PTQ4WAM selects layer-wise pre-cision together with its execution route. Calibration-guided proposals and full-model profiling screen candidate pairs before expensive task trials. The original planner or con-troller scores feasible pairs using task outcomes. Fused group rescaling and direct history reads reduce temporary storage while keeping the precision map fixed. Across 15 workloads from four model families, PTQ4WAM retains a median 99.2% of the corresponding FP32 task score. Fixed-input GPU replays show a median 2.36 × speedup and a 71.5% median reduction in peak allocated memory. These results support judging compression by task decisions and the resources needed to execute the model. LLM Usage Statement

# J. Formal Analysis and Proofs 

The analysis supports the two stages of PTQ4WAM. For precision selection we bound the expected loss in task score relative to the best map in a finite valid pool under a speci-fied source distribution. For execution, operator identities establish equivalence for a fixed set of quantized operands, and live-set accounting relates local allocation changes to the global memory peak. Runtime and allocator-reserved capacity are evaluated separately from this allocation model. Table S73 defines the notation used in the two sets of proofs. 

J.1. Notation and Probability Space 

Assumption 1 (How maps are built and how sources are sampled) . Let Fw contain all pre-development information and randomness, including calibration, Agent proposals, and candidate construction. Conditional on Fw, the ordered candidate pools and artifacts are fixed, and development source clusters Z1, . . . , Z n are independent and identically distributed from Pw, with n ≥ 1. The task score v(c, Z ) for one source, called its utility, is measurable and lies in [0 , 1] .Repeated executions or windows from a source belong to that cluster. The selector maximizes the empirical mean and resolves ties by the fixed order of the maps. Take a probability space (Ω , F , P) carrying the calibra-tion data, proposal randomness, and development clusters, and let Fw ⊆ F be the sigma-field in Assumption 1. All pools are nonempty finite subsets of the finite legal W4/W8 map space and are measurable functions of Fw. Candidate artifacts include fixed quantization statistics and any pack-ing randomness. Conditional on Fw, Zj takes values in a measurable source space Zw and v(c, ·) : Zw → [0 , 1] is fixed. For compactness, q(c) denotes E[v(c, Z ) | Fw]. This quantity can vary with the realized calibration and artifact. Source-level execution randomness is included in Zj .Utilities for repeated executions and different candidates may be dependent within a source. The assumption requires independence across source clusters, including after condi-tioning on any shared random variable. Disjoint source iden-tifiers prevent overlap, but we also assume that each source is drawn independently from its workload distribution. The Hessian proxy in Equation (S12) supplies a trace-weighted comparison criterion. Theorem 1 requires no rela-tionship between this criterion and task utility, and imposes no positivity or task-loss interpretation on Hi. Its estimator and the numerical stabilizer value are implementation details whose reporting scope is summarized in Appendix N.

First-attempt success under resource limits 

On Fast-WAM Long, 95.17% of held-out executions suc-ceeded on the first attempt without a resource fallback under PTQ4WAM, compared with 93.13% under constrained BO and 90.81% under quality-first selection (Late). The re-spective gains were 2.04 and 4.36 percentage points. This rescoring of main-paper Table 4 keeps the same 3,072 held-out parents per method and workload. If a parent triggered a fallback, all its outcomes scored zero on the first attempt. For Long, 237 of Late’s 8,606 final successes came after fallback, giving (8 ,606 − 237) /9,216 = 90 .81% . Fallback frequency counts parents, while success rates count execu-tions or windows (Tables S10–S12). On all four workloads, exhaustive Pareto-48 had the high-est first-attempt rate, followed by PTQ4WAM, constrained BO and Late (Table S110). PTQ4WAM thus ranked first among methods using 12 task evaluations. For these inde-pendent searches, the p95 limit applies to one model call per online decision. In the workload order of Table S110, the limits are 85, 45, 280 and 680 ms (Table S7). For the frozen search, the p95 limits on a complete 100-call replay are 7.60, 4.00, 24.00 and 61.00 s in the same order (Table S4). 

Relation to prior work and scope of the measurements 

Hardware-aware precision selection (HAQ), action-aware WAM quantization (SteerQuant, QuantWAMs and Q-WAM), low-bit fusion (Rudder and Marlin), and non-contiguous at-tention access motivate different parts of the design. Rudder fuses scaling and compensation for action-guided quanti-zation. For fixed codes and scales, FGR removes a ma-terialized group-rescaling intermediate and DHR removes compatible visual-history concatenation. Under the same supported format, storage target and 12-evaluation bud-get, PTQ4WAM achieved 95.37% on Fast-WAM Long and 97.43% on Goal, compared with 93.16% and 95.98% for the strongest matched adaptation (Table S13). In the matched W4A16 kernel experiment with group size 128, native Mar-lin used 7.103 s and 8,546 MB of process memory, compared with 6.514 s and 8,022 MB for the evaluated PTQ4WAM route (Table S14). Across five workloads, joint FGR+DHR reduced full-run time by 7.81–12.42% and peak allocated memory by 5.13– 9.00% relative to a tuned same-map adapter (Table S66 and Tables S102–S105). The four-way route controls isolate producer-side group rescaling and direct history reads (Ta-bles S20 and S56). FGR requires identical codes, scales, grouping and valid accumulation. DHR requires immutable history segments and unchanged logical positions, masks and normalization (Appendices J.5–J.6). Unsupported sites retain fallback routes. All 448 numerical cases met the specified FP32/FP16 tolerances (Table S62). The manifests, bitsets, run identifiers and paired measurements in Appen-dices L–M link these checks to their evaluation protocols. Of the 15 workloads, nine admit multiple legal preci-sion maps and six test execution at fixed format.
