## 摘要
训练后量化是低成本部署大语言模型的标准方式。然而，最佳量化配方会因模型和精度而异。因此，专家必须为每个新模型重新设计配方，这既耗时又常常次优。幸运的是，LLM智能体可以通过多轮构建和评估候选方案来接管这一设计过程，从而在更多轮次下得到更好的配方。然而，评估一个量化后的推理模型需要数十个GPU小时，而组合来自不同代码库的方法意味着需要手动将每种方法移植到新架构。我们提出QDA，一个由智能体为每个模型和精度设计配方的系统。为了加快评估，QDA在智能体从未见过的推理轨迹上，根据候选模型相对于原始模型的输出KL散度在几分钟内为其打分，并用长生成检查有希望的候选方案，以捕捉重复循环等失败。为了加快构建，QDA提供了一个公开PTQ方法库，这些方法彼此兼容，并且与新模型架构兼容。在四个推理模型上，QDA在W4A16、W4A8和W3A16下平均分别比最强公开配方提升0.9、1.4和2.2个百分点，每次搜索使用64个GPU小时。在320B参数的MoE模型GLM-5.3-Flash上，在NVFP4 W4A4下，它恢复了FP8模型98.3%的准确率，而最佳厂商检查点为96.9%。每个QDA检查点也都能在现有服务内核上运行，且没有推理开销。我们将发布该库、评估器和运行框架。

## Abstract
Post-training quantization is the standard way to serve large language models at low cost. However, the best quantization recipe differs across models and precisions. As a result, experts must redesign it for every new model, which is time-consuming and often sub-optimal. Fortunately, an LLM agent can take over this design by refining the recipe over rounds of building and evaluating candidates, so that more rounds lead to better recipes. However, evaluating one quantized reasoning model takes tens of GPU-hours, and combining methods from different codebases means porting each to the new architecture by hand. We present QDA, a system in which an agent designs the recipe for each model and precision. To make evaluation fast, QDA scores each candidate in minutes by its output KL divergence from the original model on reasoning traces that the agent never sees, and checks promising ones with long generations to catch failures such as repetition loops. To make building fast, QDA provides a library of public PTQ methods that are compatible with one another and with new model architectures. Across four reasoning models, QDA improves accuracy over the strongest public recipe by 0.9, 1.4 and 2.2 percentage points on average at W4A16, W4A8 and W3A16, using 64 GPU-hours per search. On the 320B-parameter MoE model GLM-5.3-Flash at NVFP4 W4A4, it recovers 98.3% of the FP8 model's accuracy, against 96.9% for the best vendor checkpoint. Every QDA checkpoint also runs on existing serving kernels with no inference overhead. We will release the library, the evaluator and the harness.

## 1. 核心问题与研究动机

- **背景**：训练后量化（PTQ）是低成本部署大语言模型的标准手段。现有 PTQ 方法各自消除不同来源的量化误差（如 SmoothQuant 处理激活离群值、AWQ 做通道缩放、GPTQ 做误差补偿、QuaRot/SpinQuant 做正交旋转、OmniQuant 类方法做端到端调参），因此**方法可以叠加组合**，组合常优于单一方法。
- **核心痛点一：配方因模型与精度而异**。论文用大量实证表明：
  - 同一精度（W4A16）下，Qwen3.5-9B 上 ParoQuant 最优、Qwen3.8-27B 上 AWQ 最优、R1-Llama 上 GPTQ 最优；
  - 同一模型（Qwen3.5-9B）换精度后排名反转：AWQ 在 W4A16 比 GPTQ 高 5.1 分，在 W3A16 反而低 12.3 分；
  - 单一技巧也可能“帮一个、害三个”（如 FP8-aware GPTQ 在 Qwen3.5-9B 上 +5.3 分，在其余三个模型上均为负收益）。
  - 产业实践（如 NVIDIA ModelOpt）为 28 个模型各维护一份手写配方，而 2025.10–2026.09 有 90+ 个 10B 以上开源模型发布，按四种精度需 360+ 份配方，**手工设计不可扩展**。
- **核心痛点二：评估极贵**。推理模型需生成长链思维（数万 token），单题多次采样才能得到可靠估计；一次完整评估需 23–86 GPU 小时，而一次搜索若只评估少数候选则搜索面太窄。
- **核心痛点三：构建极贵**。多数 PTQ 方法是各自论文的科研代码，混用需手工移植到新架构（线性注意力混合、细粒度 MoE）；即便工具包支持，速度也可能过慢（llm-compressor 0.13 对 256 专家 MoE 跑一次 GPTQ 约 16 GPU 小时）。让智能体自行填补这些缺口，每次搜索要写约 3k 行量化代码，最终精度仍更低。
- **整体含义**：论文主张把“量化配方设计”视为一个可由 LLM 编码智能体**闭环试错**完成的优化任务，并为此补齐“评估快”与“构建快”两项基础设施，使配方搜索成为可规模化、无人工干预、可复现的流程。

## 2. 方法论

### 2.1 核心思想
智能体在“提议配方 → 库构建检查点 → KL 分钟级打分 → 少量长生成复查”的四步循环中迭代，预算耗尽时提交自认为最佳的检查点，**仅该检查点**在测试基准上做完整评估。为防作弊，评估器、参考轨迹与测试集对智能体不可见。

### 2.2 问题形式化
- 配方定义为有序方法列表 + 各方法设置 + 校准数据，把原模型 M 变为量化检查点。
- 目标：在 GPU 预算 B 内最大化四类能力（数学、科学、代码、指令遵循）的平均准确率 A：
  max_i A(x(i)) s.t. Σ c(i) ≤ B。
- 由于 A 单次测量需 23–86 GPU 小时，搜索改用 KL 与生成检查排序，A 只在最终检查点上测。
- **可接受配方约束**：必须保持公开基线的量化模块、位宽与格式，能在其内核上运行且不引入新算子；公开检查点可被精修但不能原样提交。

### 2.3 关键技术细节
- **KL 代理指标**：以候选检查点与原模型 next-token 分布的 KL 散度（式 5）在“参考轨迹”（原模型对数学/科学/代码/写作规划提示自生成的推理轨迹，与测试集不重叠）上求平均。
  - 相较逐层误差（式 3），KL 能看到跨层累积误差与内核引入的误差（如 W4A8 内核的 FP8 scale）。在 44 对检查点上，KL 排序与准确率一致率 82%，逐层误差仅 73%。
  - **top-k 估计**：每位置只保留原模型概率最高的 k=128 个 token 加一个“其余”桶（式 6），将全词表 KL 估计为合并桶后的 KL；由 log-sum 不等式，估计值不超过真实 KL，实测仅低 0–0.4%。原模型 top-k 分布一次性缓存（约 1 GB），避免存储 0.21–0.56 TB 的完整分布。
  - **平局标记**：KL 差小于 σ（同一配方在不同校准子集上重建的 KL 相对标准差，0.5–1.6%）视为平局，避免智能体对随机波动过拟合。
- **长生成检查**：量化可能使推理模型“想得更久”甚至陷入重复循环、截断。智能体自选难题让候选写完整答案，统计错误/循环/截断数量，与 KL 一起决策（例：某候选 KL 降 30% 但 191 个答案中 12 个截断，触发智能体改换校准数据并加入对量化模型自身长答案的 scale 蒸馏）。
- **可组合库（21 种方法）**：覆盖变换（Hadamard 旋转、通道置换、AWQ 缩放）、舍入（RTN、GPTQ、GPTAQ、GSQ、AutoRound、GuidedQuant 等）、scale 与调优（min-max/MSE/Hessian 加权 MSE、FP8 scale 网格、scale-only 蒸馏）、校准数据（自生成与混合）、组合（模块拼接、head/embedding 格式）。
  - **架构无关**：从模型自身推导“哪个归一化层喂哪个线性层”并数值校验，新架构只需少量适配代码（GLM-5.3-Flash 仅 72 行）。
  - **对齐服务内核**：按内核实际存储精度（如 FP8 scale）选码，而非按量化器假设的 BF16。
  - **批处理 GPTQ**：同层各专家是独立同形问题，堆叠二阶统计量做一次批量分解，256 专家 MoE 的 GPTQ 从约 16 GPU 小时降到 0.42 GPU 小时，KL 与 llm-compressor 相差 1% 以内。
- **评估器**：在 vLLM worker 内挂钩 prompt log-prob，就地归约为式 6 的项，只输出运行和；只跑候选检查点，使用最终评估同款内核，比完整评估便宜 350–990×。
- **Harness**：智能体在无 GPU、无网络（仅模型 API）的沙箱中工作，外部 supervisor 记录每次工具调用；评估器在沙箱外以只读副本运行；评分任务读冻结检查点、只返回 KL。单一优先队列调度所有 GPU 任务，KL 评分优先于排队中的构建；实测 KL 评分中位 5 秒启动，GPU 利用率 72%。
- **智能体接口**：仅四条命令——`qda`（构建配方）、`kl`（打分）、`qsched`（提交其他 GPU 任务）、`handin`（提交最终检查点）。
