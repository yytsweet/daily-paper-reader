ABSTRACT
Post-training quantization is the standard way to serve large language models at low cost. However, the best
quantization recipe differs across models and precisions. As a result, experts must redesign it for every new
model, which is time-consuming and often sub-optimal. Fortunately, an LLM agent can take over this design by
refining the recipe over rounds of building and evaluating candidates, so that more rounds lead to better recipes.
However, evaluating one quantized reasoning model takes tens of GPU-hours, and combining methods from
different codebases means porting each to the new architecture by hand. We present QDA, a system in which
an agent designs the recipe for each model and precision. To make evaluation fast, QDA scores each candidate
in minutes by its output KL divergence from the original model on reasoning traces that the agent never sees,
and checks promising ones with long generations to catch failures such as repetition loops. To make building
fast, QDA provides a library of public PTQ methods that are compatible with one another and with new model
architectures. Across four reasoning models, QDA improves accuracy over the strongest public recipe by 0.9, 1.4
and 2.2 percentage points on average at W4A16, W4A8 and W3A16, using 64 GPU-hours per search. On the
320B-parameter MoE model GLM-5.3-Flash at NVFP4 W4A4, it recovers 98.3% of the FP8 model’s accuracy,
against 96.9% for the best vendor checkpoint. Every QDA checkpoint also runs on existing serving kernels with
no inference overhead. We will release the library, the evaluator and the harness.

INTRODUCTION
Large language models (LLMs) excel at mathematics, sci-
ence and programming, and reasoning models go further by
thinking for thousands of tokens before they answer (Guo
et al., 2025; Yang et al., 2025a; Chen et al., 2026). However,
serving them is costly in both memory and compute. Post-
training quantization (PTQ) is a standard way to cut both
costs (Frantar et al., 2023; Lin et al., 2024b). For example,
with its weights in NVFP4, the 320B-parameter GLM-5.3-
Flash (Z.ai, 2026) fits on one GB300 GPU instead of the two
that it needs in FP8. Quantizing the activations as well lets
matrix multiplications run on low-precision tensor cores,
which are several times faster than BF16 ones (Xiao et al.,
2023; Lin et al., 2025; Alvarez et al., 2025).
Existing PTQ methods fix different sources of quantization
error (Xiao et al., 2023; Frantar et al., 2023; Lin et al.,
2024b), so they can be stacked, and a combination often
works better than any single method (Ashkboos et al., 2024;
Liu et al., 2025b). A quantized checkpoint is therefore
produced by a recipe, which consists of the stacked methods,
their settings and their calibration data (§ 2.2). However, we
find that the best recipe differs across models and precisions.
For example, with 4-bit weight-only quantization, the most
accurate public recipe is ParoQuant (Liang et al., 2026) on

because every new model needs its own recipes and new

need over 360 recipes at our four precisions.
LLM coding agents already write code to improve algo-
rithms, GPU kernels and computer systems (Novikov et al.,
2025; Cao et al., 2026; Cheng et al., 2025). Recipe design
is a natural task for such an agent, because it also proceeds
by trial and error, building and evaluating one candidate
after another as an expert would. However, two problems
stand in the way. First, evaluating a candidate is expensive.
Because a reasoning model writes thousands of tokens per
answer and each problem must be sampled many times, a
full evaluation of one quantized checkpoint takes up to 86
GPU-hours (§ 3.2). At this cost, a search can try only a
few candidates, so a wider search needs a much cheaper
proxy metric for accuracy. Second, building a candidate
is costly. Most PTQ methods are released as separate re-
search code, so a recipe that mixes them must be ported
by hand to each new architecture, such as linear-attention
hybrids (Yang et al., 2025b; Kimi Team et al., 2025) and
fine-grained mixtures of experts (DeepSeek-AI et al., 2024;
OpenAI et al., 2025). Even a method that a toolkit supports
can be too slow for a search (§ 3.3). An agent that fills these
gaps itself writes about 3k lines of quantization code per
search and still ends with a less accurate checkpoint (§ 6.3).
To this end, we present QDA, a system in which an agent
designs the quantization recipe for each model and preci-
sion (Figure 3). To address the first problem, we use the KL
divergence of the candidate’s next-token distributions from
the original model’s as the proxy metric, measured on refer-
ence traces, reasoning traces that the original model wrote.
Because the original model’s distributions are cached, scor-
ing a candidate takes minutes, which is 350–990× cheaper
than a full evaluation. The agent also generates full answers
for a few promising candidates to reveal rare failures such
as repetition loops. To address the second problem, we im-
plement 21 PTQ methods in one library behind a common
interface. Every method takes a quantized checkpoint as
input and returns one, so the agent can stack methods in
any order. Finally, a harness runs the search without human
supervision and keeps the test benchmarks and the reference
traces out of the agent’s reach, because a recipe tuned on
them would score higher without being any better (Kapoor
et al., 2025; Xu et al., 2024).
On four reasoning models that span dense Transformers,
linear-attention hybrids and mixture-of-experts (MoE) mod-
els, QDA improves the average accuracy over the strongest
public recipe by 0.9, 1.4 and 2.2 points at W4A16, W4A8
and W3A16 (Figure 1). Each search uses 64 GPU-hours.

2.2
Post-Training Quantization Methods
Post-training quantization (PTQ) quantizes a trained model
without retraining it, using only a small set of calibration
texts. Most methods work one linear layer at a time and
minimize its output error on the calibration inputs X:

A recipe makes four choices: a transformation, a rounding
method, the scales and their tuning, and the calibration data.
Transformations.
Since XW⊤= (XT−1)(WT⊤)⊤
for any invertible T, a transformation can reshape both
operands without changing the output, for example to tame
the outliers in a few activation channels (Xiao et al., 2023).
A diagonal T rescales channels: SmoothQuant moves out-
liers from the activations into the weights (Xiao et al., 2023),
and AWQ scales up the weight channels that meet large ac-
tivations, protecting them from rounding (Lin et al., 2024b).
An orthogonal T, such as a Hadamard rotation, mixes all
channels so that none stands out (Ashkboos et al., 2024; Liu
et al., 2025b; Xi et al., 2023). ParoQuant combines learned
pairwise rotations with channel scaling (Liang et al., 2026).
Rounding.
Rounding each weight to the nearest code
ignores how the errors of different weights add up in the
output. GPTQ (Frantar et al., 2023) solves Equation (3)
approximately: it rounds one column at a time and up-
dates the columns not yet rounded to cancel the error, using
the second-order statistics X⊤X of the calibration inputs.
Learned rounding, such as AutoRound (Cheng et al., 2024)
and GSQ (Dadgarnia et al., 2026), instead learns the round-
ing of each weight by gradient descent, at a higher cost.
Scales and tuning. A larger scale covers the extreme values
but rounds the others coarsely, so clipping searches for the
scale that best balances the two. Since Equation (3) cannot
see errors that build up across layers, tuning methods train
the scales so that the quantized model matches the original,
block by block (Shao et al., 2024; Chen et al., 2025) or by
distillation (Malinovskii et al., 2024).
Calibration data. Every statistic above comes from the
calibration inputs, so their choice alone changes the accu-
racy of the result (Williams & Aletras, 2024). Generic text
is the default, and text that the original model generates
(self-generated data) can work better (Williams et al., 2025).
Combining the steps.
Because each choice removes a
different error, applying them in sequence, for example a
rotation followed by GPTQ, is often more accurate than any
single method (Ashkboos et al., 2024; Liu et al., 2025b).
Yet steps that treat the same error overlap, so the best com-
bination cannot be predicted from each method alone.
3
MOTIVATION
3.1
The Best Recipe Differs per Model and Precision
At W4A16, no public recipe is the most accurate on every
model (Figure 2(a)). ParoQuant is the best on Qwen3.5-9B,
AWQ on Qwen3.8-27B and GPTQ on DeepSeek-R1-Distill-
Llama-8B. On a single model, the ranking also changes with
the precision. On Qwen3.5-9B, AWQ is 5.1 points more
accurate than GPTQ at W4A16 but 12.3 points less accurate
at W3A16. Even a single technique can help one model and
hurt the others. For example, the W4A8 kernel stores each
scale in FP8, whereas GPTQ computes with BF16 scales.
Running GPTQ with the FP8 scales instead (FP8-aware
GPTQ) raises the accuracy of Qwen3.5-9B by 5.3 points but
lowers it on the other three models (Figure 2(b)). A recipe

found for one model and precision therefore does not carry
over, and each new pair needs its own search.
3.2
Evaluating a Recipe Is Expensive
Earlier searches over quantization recipes could evaluate
each candidate in minutes. AutoML for convolutional net-
works measured accuracy on a small validation set (He et al.,
2018; Wang et al., 2019), and previous LLM quantization
methods were judged by short benchmarks that need only a
few generated tokens per question (Frantar et al., 2023; Lin
et al., 2024b).
Reasoning models break this assumption. They are graded
on the final answer after a long chain of thought, which often
runs to tens of thousands of tokens, and one different token
can change the rest of the reasoning and the answer (Yuan
et al., 2025). A reliable estimate therefore averages many
samples per problem, especially since AIME holds only tens
of problems (Hochlehnert et al., 2025), so a full evaluation
of one quantized checkpoint generates about ten thousand
long answers and takes 23 GPU-hours on DeepSeek-R1-
Distill-Llama-8B and 60–86 GPU-hours on our Qwen mod-
els (Figure 2(c)). Fewer problems or samples make the
estimate too noisy, and scoring every candidate on the test
sets would overfit them (Blum & Hardt, 2015). A search
therefore needs a proxy metric that takes minutes yet reflects
the whole served model.
3.3
Building a Candidate Is Costly
Building a candidate is costly in two ways. First, a recipe
can use only methods whose code runs on the model’s ar-
chitecture. Most PTQ methods are released as research
code for the model families in their papers. Toolkits such
as llm-compressor, AutoRound and ModelOpt run only
the methods that they have reimplemented and extend per-
architecture tables by hand for each new model (Red Hat
AI & vLLM Project, 2024; Cheng et al., 2024; NVIDIA,
2024), so llm-compressor took three weeks after the release
of Qwen3-Next to support calibration on it (Sikka, 2025).
Second, a build can be too slow for a search. For example,
one GPTQ build of the 256-expert Qwen3.6-35B-A3B with
llm-compressor 0.13 takes about 16 GPU-hours, a quarter
of the 64 GPU-hours that we give each search. Without
our library, the agent fills these gaps itself, writing about 3k
lines of quantization code per search, and still ends with a
less accurate checkpoint (§ 6.3). Our library fills them once
for all searches. It derives which layers feed which from the
model itself, so a new architecture such as GLM-5.3-Flash
needs no per-method changes, and it builds this GPTQ in
0.42 GPU-hours (§ 5.1).
4
QDA: RECIPE DESIGN BY AN LLM
AGENT
As shown in Figure 3(a), the agent designs a recipe in a loop
of four steps. In each round, (1) the agent proposes a recipe,
(2) the library builds it into a candidate checkpoint, and
(3) the evaluator scores the checkpoint by its KL divergence
from the original model, which takes minutes. For a few
promising candidates, (4) the agent also generates long
answers to find failures such as repetition loops. When
the budget runs out, the agent submits the checkpoint it
considers best, and only this checkpoint is evaluated on the
test benchmarks. § 5 describes the system.
4.1

with its settings and calibration data, that turns the original
model M into a quantized checkpoint.

them by the mean accuracy A of a full evaluation over
math, science, code and instruction following, the categories
that model releases report (Guo et al., 2025; Yang et al.,
2025a), and average the categories as recent quantization
work does (Liang et al., 2026). Within a GPU budget B, the

data with the original model. Between proposals, it reads the
log of its scores, the results of its checks and its own notes,
and from them decides which step or setting to change next.

Why the KL. We start from the signal that most PTQ meth-
ods already compute, the layer-wise error of Equation (3),
which GPTQ and AWQ minimize. However, it looks at
one layer at a time and cannot see the errors that build up
across layers. For example, on Qwen3.5-9B at W4A16, the
layer-wise error prefers GPTQ over AWQ, although AWQ’s
A is 5.1 points higher. We therefore compare the whole
quantized model with the original one, by the KL diver-
gence between their next-token distributions. The evaluator
computes these distributions on the quantized checkpoint
as vLLM serves it, so the KL also includes errors that only
the serving kernel introduces, such as the FP8 scales of the
W4A8 kernel (§ 3.1). To verify this choice, we take 44
pairs of public baselines and simple recipes at three preci-
sions (Figure 2(c)). The KL orders 82% of the pairs as their
accuracy does, against 73% for the layer-wise error.

4.3
Checking Long Answers
Only the answer after the thinking is graded, so a model
that loops or never finishes its reasoning loses the whole
problem. Quantization can make this more likely, as quan-
tized reasoning models can think longer than the original
model (Lotfi et al., 2026). These failures tend to appear late
in long answers, so they show up only when a checkpoint
writes complete answers itself. In step (4), the agent there-
fore picks a candidate and has it write full answers to hard
problems that the agent chooses itself, none of which come
from the test benchmarks. It counts the answers that are
wrong, loop or are cut off, and weighs these counts together

5
THE QDA SYSTEM
A search must build and score dozens of checkpoints within
its budget, safely and without human intervention. QDA
makes this possible with three components, a composable
library, an evaluator inside the serving engine and a harness
that runs the search (Figure 4). The agent can write any code
in its sandbox, but every GPU job, including its own code,
goes through the harness, so that one scheduler shares the
GPUs of a search and keeps to its budget (§ 5.3). The agent
reaches the three components through four commands, qda
to build a recipe, kl to score a checkpoint, qsched for any
other GPU job and handin to submit its final checkpoints.
5.1
Composable Library
Our library extends llm-compressor (Red Hat AI & vLLM
Project, 2024) to 21 methods covering § 2.2 (Table 8).
Composing methods across architectures. Applying any
method to a checkpoint that vLLM can load produces a
new checkpoint that vLLM can also load. Methods there-
fore stack as the steps of a recipe, and a method can also
refine a public checkpoint or one that the agent built itself.
Methods such as AWQ and rotations must know which nor-
malization layer feeds which linear layers, and research
code hardcodes these module names for each model family.
Our library instead derives these relations from the model
itself and checks each of them numerically, so a method
written once runs on new architectures. After the library
was built, supporting GLM-5.3-Flash, a 288-expert model
unseen by our main searches, took a 72-line adapter and
an extension for its FP8 release and multi-token-prediction
layer. Every method then ran on it, and the search needed
no other development (§ 6.2, App. D).
Matching the serving kernel. A kernel can store a quantity
at lower precision than the quantizer assumes. For example,
vLLM’s W4A8 kernel casts each scale to FP8, whereas llm-
compressor picks the codes for BF16 scales. The library
picks the codes for the scales that the kernel stores.
Fast builds. In llm-compressor 0.13, GPTQ solves each
linear layer in turn, so one layer of 256 experts runs 768
small solves one after another. The experts of a layer are in-
dependent problems of the same shape, so the library stacks
their second-order statistics and solves all of them with one
batched factorization. One GPTQ build of Qwen3.6-35B-
A3B thus takes 0.42 GPU-hours instead of about 16, with a
KL within 1% of llm-compressor’s.
5.2
Evaluator
Equation (5) needs both models’ full-vocabulary next-token
distributions at about a million positions. A naive evalu-
ator would run both models for every score. Moreover, a
serving engine such as vLLM returns only the few largest
probabilities at each position. The evaluator thus caches the
original model’s top-k distributions once (about 1 GB) and
computes the candidate’s side inside the engine.


QDA: Closed-Loop LLM Quantization Design with Agents
Reducing inside the engine. The evaluator hooks vLLM’s
prompt log-probabilities inside its workers and reduces each
full-vocabulary distribution to the terms of Equation (6) in
place, so only running sums leave the engine. A score thus
runs only the checkpoint, on the final evaluation’s kernels,
and is 350–990× cheaper than a full evaluation (App. C).
5.3
Harness
A search runs without human intervention, so the harness
itself must keep the evaluation honest and the GPUs busy.
Isolating the evaluator. If the agent could read its evalu-
ator, it could lower the KL without improving the model,
for example by calibrating on the reference traces them-
selves (Lin et al., 2024b). The harness therefore keeps the
reference traces and the test benchmarks out of the agent’s
reach. The agent works in a sandbox with no GPU and no
network except the model API, and a supervisor outside it
checks and logs every tool call (App. E). The evaluator runs
outside the sandbox from a read-only copy of its code. Each
scoring job reads a frozen copy of the checkpoint and returns
nothing but KL values. These are the overall KL, the KL
per domain and the KL on human-written text. Every file
the agent can read is scanned for test items beforehand, so
that no test problem can reach the agent through calibration
data or prompts (App. C).
Scheduling. A search runs dozens of GPU jobs, from KL
scores of a few minutes to builds of several hours, and the
agent submits them one by one as it works. The agent waits
for each KL score before its next step, but scores and builds
run on the same GPUs. Since the agent has no GPU in its
sandbox, the harness holds these GPUs for the whole budget
and runs every job from one priority queue. A job states
how many GPUs it needs, how long it expects to run and
which jobs it waits for. The harness copies the job’s script
when the job is submitted, so the agent can keep editing
its files while the job waits or runs, and it runs the job in
a container on GPUs that no other job uses. KL scores go
ahead of queued builds without stopping running ones, and
no job starts if its expected duration runs past the deadline.
Over the 12 searches, a KL score starts a median of 5 s after
the agent asks, and jobs keep the GPUs busy 72% of the
time.

Setup
Models and precisions. We evaluate four reasoning models

We use the formats and vLLM kernels of Table 1 on GH200

Benchmarks.
The test benchmark has four categories,
and we report their mean. They are math (AIME 2025 and

Baselines.
The public recipes are GPTQ (Frantar et al.,
2023) and AWQ (Lin et al., 2024b) with the defaults of llm-
compressor, QuaRot’s offline rotations followed by default

and two recent methods that report state-of-the-art accuracy,
ParoQuant (Liang et al., 2026) at W4A16 and GSQ (Dadgar-
nia et al., 2026) at W3A16. GPTQ is asymmetric at W4A16.
ParoQuant uses its released checkpoints. GSQ uses its re-
leased checkpoint on Qwen3.8-27B, and on the other three
models we run its official code ourselves (App. A). Both
ParoQuant and GSQ train the quantized model. ParoQuant
takes about 9 GPU-hours on an 8B model (Liang et al.,
2026), and GSQ took 30–52 GPU-hours per model on our
GPUs, close to the 64 GPU-hours of one search.
Agents and budget. The agent is Claude Code v2.1.303
with Claude Opus 5.5 at high effort, and one task statement
serves every model and precision (App. E). Each model–
precision pair gets one search with 8 GH200 GPUs for 8
hours (64 GPU-hours) and $19–75 of agent tokens, and

is not charged to it. On Qwen3.6-35B-A3B, which the
ablations also use, each precision gets three searches, and
we report their mean (standard deviation 0.1–0.2 points).
Like a human expert, the agent may start from a public
checkpoint (§ 4.1).

6.3
Ablation Study
Table 5 replaces one component of QDA at a time on
Qwen3.6-35B-A3B, where builds cost the most.
Replacing the agent. To test whether the agent matters,
we replace it with two search algorithms, greedy search
and ASHA (Li et al., 2020), that search the same library
(App. E). QDA beats both by 0.2–1.2 points at W4A8 and
W3A16, and they come within 0.1 points at W4A16.
Replacing the infrastructure.
To test our library and
harness, we give the agent public libraries and a plain GPU
queue, and it writes the rest of the code itself (App. E). Over
three searches, QDA is 0.2–0.5 points more accurate on
average and varies less (standard deviation 0.1–0.2 against
0.2–0.4 points). Without the library, the agent rebuilds parts
of it, such as an FP8-aware GPTQ, and writes three times
as much code (3.1k against 1.1k lines on average). It never
tries a rotation, the step behind QDA’s largest gap at W4A8.
It launches 50% more jobs and loses twice the GPU-hours
to failed or cancelled ones (6.6% against 3.1%).
A fixed recipe. Five of QDA’s 12 final recipes follow the
same pattern: GPTQ calibrated on self-generated data, then
scale distillation. To test this pattern alone, we fix its settings
and apply it as a fixed recipe without a search (Table 5b,
App. A). This pattern was found by QDA’s searches, so the
fixed recipe is not an independent baseline. At W4A16, it
matches or beats the best public recipe on all four models,
yet stays below QDA on each. On Qwen3.5-9B, it is 2.2
and 5.0 points below QDA at W4A8 and W3A16, so even
this fixed recipe does not carry over.
6.4
What the Searches Found
The 12 final recipes differ in every stage (Figure 6), and the
search logs show two reasons.
No published practice helps every model and preci-
sion. As Figure 5(a) shows, each of four published practices
that the searches tried lowered the KL on one model and
not on another. At W4A16, calibrating on self-generated

data (Williams et al., 2025) lowers the KL of Qwen3.6-
35B-A3B by 30% but raises it on R1-Llama, whereas scale
distillation on the default calibration text helps R1-Llama
and not Qwen3.6-35B-A3B. AWQ’s scaling cuts the KL
of Qwen3.5-9B by a third but adds almost nothing after a
Hadamard rotation, which treats the same outlier channels.
A plausible reason is that each practice fixes one source of
error and helps only where that source dominates. Across
whole recipes, the step that lowered the KL most also differs,
a rotation in five searches, distillation in four, self-generated
data in two and an FP8 scale search in one (Figure 5(b)).
The agent builds its own data and code. Every final recipe
calibrates or distills on self-generated data for prompts that
the agent chose. In addition, 10 of the 12 train on answers
that the quantized model itself wrote. Five also keep code
that the agent wrote for training or merging. For example,
with the codes fixed, the agent’s distillation also trains the
parameters that the format leaves in BF16, such as normal-
ization gains and the gate and convolution parameters of
Gated DeltaNet, and none of them adds inference cost. In
five of the ten, the agent added this training right after a gen-
eration check found loops or cut-off answers (§ 4.3). It also
diagnosed problems from its logs (bold notes in Figure 5(b)).
On Qwen3.5-9B at W4A16, it traced spikes in its distillation
loss to BF16 scales that crossed a rounding boundary all at
once, which made Adam’s steps jump, and raised Adam’s ϵ.
On DeepSeek-R1-Distill-Llama-8B at W3A16, it found that
its own rounding code gave the scales a zero gradient and
fixed it. On Qwen3.8-27B at W4A8, it skipped distillation,
because the kernel stores each scale in FP8 and the smallest
change to an FP8 scale rescales its whole group of weights
by at least 6%, too large a step to fine-tune.

RELATED WORK
Quantization of LLMs.
Weight-only methods (Frantar
et al., 2023; Lin et al., 2024b; Dettmers et al., 2024; Tseng
et al., 2024a;b; Egiazarian et al., 2024; Liang et al., 2026;
Dadgarnia et al., 2026) speed up memory-bound decoding.
Weight-activation methods (Xiao et al., 2023; Ashkboos
et al., 2024; Liu et al., 2025b; Lin et al., 2024a; Zhao et al.,
2024; Lin et al., 2025) also run the matrix multiplications in
low precision, and recent work extends quantization to 4-bit
microscaling formats (Rouhani et al., 2023; Alvarez et al.,
2025) and to the recurrent states of linear attention (Pan
et al., 2026). Benchmarks (Gong et al., 2024) and large-
scale studies (Kurtic et al., 2025; Liu et al., 2025a; Lian
et al., 2026) compare fixed recipes to distill best practices.
The calibration data (Williams & Aletras, 2024; Williams
et al., 2025) and tuning against the original model (Shao
et al., 2024; Chen et al., 2025; Malinovskii et al., 2024)
change the result further, and the KL divergence from the
original model is a common way to compare quantized
checkpoints (Dutta et al., 2024; Kawrakow, 2024). QDA
searches for the combination of these methods, settings and
data for each model and precision.
Automated quantization search. AMC (He et al., 2018),
HAQ (Wang et al., 2019) and APQ (Wang et al., 2020)
searched per-layer pruning ratios, bit-widths and architec-
tures of CNNs, with the hardware in the loop. For LLMs,
AMQ (Lee et al., 2025) and EvoPress (Sieberling et al.,
2025) search per-layer bit-widths, OptiKIT (Santavas et al.,
2026) runs a user-chosen recipe on several calibration sam-
ples and tunes serving parameters, and HAQA (Deng et al.,
2026) tunes fine-tuning hyperparameters and kernel settings
with an LLM agent, but none of them searches over combina-
tions of PTQ methods, their settings and calibration data at
a fixed precision. ModelOpt’s recipe-search skill (NVIDIA,
2026b) has a coding agent choose among ModelOpt’s built-
in formats, calibration algorithms and quantized modules,
and it writes no new methods or data. EvoPress also scores
by KL, but on models stitched from precomputed layers, not
on the served checkpoint.
LLM agents as optimizers.
LLM agents optimize
prompts (Yang et al., 2024), algorithms (Romera-Paredes
et al., 2024; Novikov et al., 2025), post-training recipes (Liu
et al., 2026), GPU kernels (Ouyang et al., 2025; Baronio
et al., 2026; Cao et al., 2026; Xing et al., 2026) and mecha-
nisms of computer systems (Cheng et al., 2025; Hamadanian
et al., 2026; Zhao et al., 2026). ML engineering and research
agents follow a validation score (Chan et al., 2025; Toledo
et al., 2025) and can overfit or game it (Von Arx et al.,
2025; Zhong et al., 2026), which AIRA2 (Hambardzumyan
et al., 2026) counters by hiding its search split from the
agent. QDA instead scores candidates in minutes with an
agent-invisible KL evaluator and evaluates only the final
checkpoint on the test benchmarks.

CONCLUSION
We present QDA, a system in which an LLM agent designs
the quantization recipe for each model and precision, be-
cause the best recipe differs across them. QDA scores each
candidate in minutes by its output KL divergence from the
original model on reference traces that the agent never sees,
checks a few promising candidates with long generations,
and builds them with a library of public PTQ methods that
compose and run on new architectures. On four reasoning
models, it improves average accuracy over the strongest
public recipe by 0.9–2.2 points. Given ModelOpt’s work-
flow and tools instead, the same agent falls 0.5–1.3 points
behind. On the 320B-parameter GLM-5.3-Flash at NVFP4,
it recovers 98.3% of the FP8 accuracy, against 96.9% for
the best vendor checkpoint. Every QDA checkpoint adds no
inference overhead.

BASELINES
Defaults. GPTQ uses llm-compressor’s GPTQModifier
with its preset for each precision. The preset is symmetric
with g = 128, a damping fraction of 0.01, static activation
order and a min-max observer. At W4A16, Table 2 reports
the asymmetric variant. AWQ uses AWQModifier with
its defaults (duo scaling, a grid of 20) followed by round-to-
nearest, asymmetric at W4A16 and symmetric at W3A16.
W4A8 uses FP8 (E4M3) activations with dynamic per-token
scales. Within one model and precision, every row of Ta-
ble 2 quantizes the same modules at the same bit width.
At W3A16, the output head and the token embeddings are
INT4 with g = 64 in every row, as in GSQ’s release.
ParoQuant and GSQ. ParoQuant uses the checkpoints
released by its authors, served on vLLM 0.27.1 with its
official rotation kernel. Its vLLM backend had no MoE sup-
port, so we added it for Qwen3.6-35B-A3B with 176 lines
of code. GSQ uses the released checkpoint on Qwen3.8-
27B and the official code and configuration on Qwen3.5-
9B, Qwen3.6-35B-A3B and DeepSeek-R1-Distill-Llama-
8B. On Qwen3.6-35B-A3B, the official code needed six
patches of about 220 lines in total. Its MoE path skipped
the attention layers, so we ported the attention stage of its
dense path to quantize attention as in the other rows. The
other patches fixed layer names and a compressed-tensors
call that no longer matched the model and the library. On
DeepSeek-R1-Distill-Llama-8B, we use the configuration
that its README gives for Llama models.
QuaRot+GPTQ.
We fuse QuaRot’s Hadamard rota-
tions (Ashkboos et al., 2024) into the BF16 weights offline
and then run the default GPTQ recipe of the W4A8 row
unchanged, with the same calibration data. On DeepSeek-
R1-Distill-Llama-8B, we apply R1 to the residual stream
and R2 to the value and output projections of each attention
head. On the Qwen models, we apply R1 only, because the
gate before each attention output projection and the Gated
DeltaNet layers make R2 inexact. QuaRot’s online rota-
tions (R3 and R4) would add inference operators, which the
formats of Table 1 do not allow, so we leave them out.
FP8-aware GPTQ and the fixed recipe. FP8-aware GPTQ
(Figure 2(b), § 3.1) is built from scratch with the default
calibration data on each model, and its W4A8 averages are
62.5, 76.4, 76.7 and 42.7 on Qwen3.5-9B, Qwen3.6-35B-
A3B, Qwen3.8-27B and DeepSeek-R1-Distill-Llama-8B.
The fixed recipe of Table 5b is the pattern that five QDA
searches found (§ 6.3). It runs GPTQ on self-generated data,
a pool of 640 answers that the BF16 model wrote (2,048
samples of 2,048 tokens). It then runs two rounds of 200
steps of scale distillation on the same pool, at learning rates
3 × 10−4 and 10−4, from scratch on every pair.

DATA, CONTAMINATION AND THE
EVALUATOR
Calibration data. The baselines are calibrated on 2,048
texts (0.91–0.96M tokens), 1,536 from llm-compressor’s
default mix and 512 from UltraChat. No 20-gram of these
texts occurs in any test benchmark. The agent may build
its own data only from allow-listed public datasets, from
which every row that holds a test item is removed by 20-
gram matching before the search. Every file that the agent’s
container can read is then scanned against the test items,
with one positive control per benchmark, and a single hit
stops the search. Every search in this paper passed with no
hit.
The reference traces. The reference traces are two BF16
continuations for each of 48 prompts from AIME 2000–
2020, SuperGPQA, OpenThoughts and OpenHermes. They
are checked against every test benchmark and the calibra-
tion data by id, normalized-text hash and 13-gram matching,
with no hit. The noise σ is the pooled within-recipe stan-
dard deviation of ln KL over two W4A16 recipes, each
rebuilt on three random subsets of the default calibration
file. It is 0.0159 on Qwen3.5-9B, 0.0047 on Qwen3.6-35B-
A3B, 0.0093 on Qwen3.8-27B and 0.0063 on DeepSeek-
R1-Distill-Llama-8B. Scoring one checkpoint twice gives
identical values, and two nodes that score the same check-
point agree within 0.2%.
Signal comparison.
The 36 checkpoints of Figure 2(c)
are 31 public baselines of Table 2, a symmetric GPTQ
on Qwen3.8-27B at W4A16, and four scripted recipes on
DeepSeek-R1-Distill-Llama-8B at W4A16. The 31 base-
lines are all those of Table 2 except the four QuaRot+GPTQ
rows and GSQ on DeepSeek-R1-Distill-Llama-8B, which
were evaluated later. The four recipes are RTN, symmetric
GPTQ, AWQ followed by GPTQ, and GPTQ calibrated on
the original model’s outputs, and every checkpoint is evalu-
ated with the protocol of Table 2. Pairs within a model and
precision whose accuracies differ by less than 0.05 points
are dropped, which leaves 44. The layer-wise error is the
median relative output error of the linear layers on BF16
inputs.
Cost of a score.
On one GH200, a KL score takes 3.2–
4.0 GPU-minutes on DeepSeek-R1-Distill-Llama-8B, 4.7–
6.1 on Qwen3.5-9B, 5.6–7.6 on Qwen3.6-35B-A3B and
8.0–11.7 on Qwen3.8-27B. One full evaluation takes 23.3–
26.0, 74.7–82.1, 59.9–86.2 and 65.1–71.7 GPU-hours on
the same models. The reference traces of our searches
cover 0.49–1.13 million positions. Their top-k cache takes
0.47–1.09 GiB, whereas full BF16 distributions would take
0.21–0.56 TB, and the bucket of Equation (6) holds on aver-
age 0.015–0.048% of the original model’s probability. On
nine checkpoints of Qwen3.8-27B and DeepSeek-R1-Distill-
Llama-8B that we scored both with the exact KL over the
full vocabulary and with the top-k estimate, the estimate is
0–0.4% lower.

Predefined searches. The greedy search and ASHA use no
LLM. A recipe takes up to two transforms, one solver and up
to two refinements from the library’s method table (Table 9),
or one or two refinements of a public checkpoint. It also
chooses its calibration data, which is the default file, a fixed
pool of 640 answers that the original model wrote before
the search, or a mix of the two. Finally, it chooses 512 or
2,048 samples of 2,048 or 4,096 tokens and the maximum
length and learning rate of distillation. The greedy search
starts from the public checkpoint with the lowest KL and
repeatedly tries, at random, an untried recipe one edit away
from the best one so far. ASHA samples recipes that start
from scratch or from the lowest-KL public checkpoint and
runs successive halving over distillation steps, with rungs
at 23, 67 and 200 steps and the top third promoted. Both
submit their three lowest-KL checkpoints, and the GPU
time to generate the pool counts against their budget. The
answers in the pool run to at most 12,288 tokens.
The task statement. Each search starts with one instruc-
tion, which tells the agent to read the task statement in full,
follow it and keep the best submitted checkpoint until the
deadline. Table 10 summarizes the statement for Qwen3.6-
35B-A3B at W4A16. It names no method to use or to avoid,
and its full text ships with the artifact. Across models, the
statement changes in the model name, the default calibration
file, the clause on the expert kernel and, on DeepSeek-R1-
Distill-Llama-8B, the length of the long-generation checks
(32,768 tokens). Across precisions, it also changes in the
goal sentence, the list of baselines and the format section.

Section
What it says
Goal
The best W4A16 checkpoint by the deadline. It is
scored later on math, code, science and instruction
following, which count equally, and nothing mea-
surable in the workspace is that evaluation.
Clock
and
resources
Two nodes of four GH200s until the deadline,
when every task is cancelled. Plan for idle GPUs
in the last hour. Run long-generation checks (up to
81,920 tokens) on the top checkpoints in all four
domains before submitting. Training data may in-
clude the quantized model’s own answers scored
by the BF16 model. When the latest checkpoints
of the current line of recipes tie in KL, try another
line. Reread the notes and failed logs every couple
of hours.
Workspace
and tools
The quantization and serving environments, offline
datasets, a format-compatibility package with no
quantization method, and the qda library: atomic
transforms, solvers and refinements to stack, plus
measurements (proxy, profiler), diagnostics
(probe) and mix. The method cards, loaded as
a Claude Code skill. New methods and subagents
are allowed.
Prior
The BF16 model and the public checkpoints with
their methods. ParoQuant is listed for reference
only, since it needs extra kernels. A public check-
point cannot be submitted unchanged.
Format
INT4, g = 128, asymmetric, on the Marlin ker-
nels; the same modules and bits as the public
checkpoints; nothing added at inference. Forbid-
den: other bit widths or per-module bits, modules
from foreign checkpoints, mixed symmetric and
asymmetric modules.
Data
No build data may contain an evaluation item or a
text of the reference traces.
KL
kl DIR checks a checkpoint and returns its KL
from the BF16 model, in total, per domain and on
human-written text. kl log lists past KL values,
and kl sens estimates which module groups
would close a KL gap. The reference traces are
hidden.
Submission
handin submit takes a ranked list; the evalua-
tor checks each checkpoint for format and a short
inference, not for answers. If no submitted check-
point passes, the public checkpoint closest to the
BF16 model is evaluated. Submitted checkpoints
must be written by jobs in the queue.
Notes
Keep a report and notes to resume from, and read
long outputs from files.
Scope
Do not look for or rebuild evaluation items, and
do not edit the evaluation, grading, serving or eval-
uator code.
